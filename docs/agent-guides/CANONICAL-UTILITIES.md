# Canonical Utilities - Full Rationale

The complete, reasoned entry for every commonly-reimplemented function in the codebase. The always-loaded index in [CLAUDE.md](../../CLAUDE.md#commonly-reimplemented-functions-do-not-add-new-copies) lists each entry as one line (name, canonical symbols, path); this file carries the why - the failure each canonical implementation replaced, the invariants it protects, and the traps that made the duplicates subtly wrong. Read the matching entry here BEFORE extending or working around one of these utilities.

Grep-verified 2026-09-04 (`npm run docs:verify` checks that every path below still resolves).

- **ID generation:** `generateId()` in `src/renderer/utils/ids.ts`, `generateUUID()` in `src/shared/uuid.ts`
- **Format file size:** `formatSize()` in `src/shared/formatters.ts`
- **Format numbers:** `formatNumber()` (compact: `1.2M`) and `formatCount()` (exact, grouped: `1,204,993`) in `src/shared/formatters.ts`. Pick by whether the digits ARE the information - a badge wants the magnitude, a filtered row count wants the number.
- **Format tokens:** `formatTokens()`, `formatTokensCompact()`, `estimateTokenCount()` in `src/shared/formatters.ts`
- **Format elapsed time:** `formatElapsedTimeColon()` in `src/shared/formatters.ts`
- **Humanized durations:** everything in `src/shared/duration.ts` (re-exported from `formatters.ts`). `humanizeDuration(ms, opts)` is the one engine; `formatDurationHuman` / `Compact` / `Verbose` / `Parts` / `Decimal` / `Long` / `Words`, plus `formatActiveTime` and `formatElapsedTime`, are presets over it. **Never hand-roll another `Math.floor(ms / 86400000)` ladder** - a dozen near-identical copies had already drifted apart on where the ladder stops, whether a zero segment is padded (`"2h 0m"` vs `"2h"`), and whether a countdown rounds up. Those are options (`units`, `maxUnits`, `style`, `keepZeroUnits`, `adjacentUnits`, `round`, `fallback`), so pick a preset or call the engine. Unit sizes are in `DURATION_MS` - don't redeclare `const DAY = 86400000`. See [SHARED-UTILS.md → Durations](docs/agent-guides/SHARED-UTILS.md#durations-srcshareddurationts---both).
- **Format profiling spans (ms):** `formatDuration()` in `src/shared/performance-metrics.ts` (NOT formatters.ts - common mistake). Two-decimal `"123.45ms"` / `"1.23s"` for perf traces only; it caps at seconds, so a multi-day span comes out as a giant seconds float. For anything user-facing use `src/shared/duration.ts`.
- **Format relative time:** `formatRelativeTime()` in `src/shared/formatters.ts`
- **Format cost:** `formatCost()` in `src/shared/formatters.ts`
- **Timestamp for a generated file name:** `fileTimestampSlug(dateOrTimestamp?)` in `src/shared/formatters.ts` - `20260713-142530`, filesystem-safe everywhere and chronologically sortable. LOCAL time on purpose: the name is read by the human who pasted the image at that wall-clock moment, so a UTC stamp reads as the wrong hour to everyone outside UTC. Both the renderer's `saveImageToProject()` and the CLI's `image save` name files with it, so a screenshot saved by hand and the same one saved by an agent cannot come out under two different conventions.
- **Summing a Codex session's tokens:** `CodexTokenCounts` in `src/shared/codexTokenUsage.ts`. Codex reports usage in two shapes and only one is per-turn: `turn.completed.usage` and `info.last_token_usage` are that turn's numbers, while `info.total_token_usage` on a `token_count` event is the running SESSION TOTAL. Summing the total across events is the trap - a session with N turns reports 1+2+...+N times its real tokens, so cost grows with the SQUARE of the conversation length, which is what turned 1.7B input tokens into 75B and let Codex outrank Claude on a dashboard driven almost entirely by Claude agents. The accumulator prefers `last_token_usage`, falls back to a cumulative DELTA, and reads a total that moves backwards as a counter restart (a resume or fork) rather than clamping it to zero. Reasoning output folds into `outputTokens`; `cachedTokens` stays a SUBSET of `inputTokens`. All three transcript scanners go through it so they cannot disagree again - do NOT hand-roll a fourth sum. It has no Electron imports so the CLI can bundle it. **Bump `CODEX_SESSION_CACHE_VERSION` in `src/main/storage/codex-session-storage.ts` whenever this math changes**: entries are reused while `fileMtimeMs` still covers the file, and a parsing fix does not touch a transcript's mtime, so old inflated numbers are served until a session is rewritten.
- **Path utilities:** `truncatePath()`, `getParentDir()`, `truncateCommand()`, `isAbsolutePath()`, `getBasename()` in `src/shared/formatters.ts`
- **Classifying a file by extension:** `getFileCategory()`, `isPreviewableFile()`, `matchesFileCategory()`, `getFileExtension()` in `src/shared/fileCategories.ts`. One table answers both "can Maestro open this?" and "which bucket is it in?" - `isPreviewableFile` is DERIVED from `getFileCategory`, so a file cannot show up under a filter pill and then refuse to open, nor be openable while invisible under every pill. Audio and video are NOT listed there; they resolve through `getMediaKind()` in `mediaTypes.ts`, which is the single source of truth for what Chromium can decode. Do NOT hand-roll another `TEXT_EXTENSIONS` set - the private copies inside `FileSearchModal` are exactly what this replaced. Distinct from the sets in `src/renderer/utils/fileExplorerIcons/shared.ts`, which exist to pick an ICON and split far more finely (lockfiles, test folders); pick by question and do not merge them.

- **Shell escape:** `shellEscape()`, `shellEscapeArgs()`, `shellEscapeForDoubleQuotes()` in `src/main/utils/shell-escape.ts`
- **SSH connection options (`ssh -o`):** `resolveSshOptions()` / `buildSshOptionArgs()` / `validateSshOption()` in `src/shared/sshOptions.ts`. FOUR sites used to build this list by hand - the agent spawn builder, the Test Connection probe, `SshCommandRunner`, and the interactive terminal tab in `ipc/handlers/process.ts` - and they had already drifted: only one set `LogLevel`, and the terminal path omitted `BatchMode` entirely, so a remote could test green and then connect with a different option set when an agent actually ran on it. The merge is CASE-INSENSITIVE, which is the whole reason it is one function: OpenSSH treats keywords case-insensitively but applies `-o` FIRST-WINS, so a naive spread emitting both `-o ConnectTimeout=10` and `-o connecttimeout=45` silently keeps the 10 and the user's override does nothing. A command-line `-o` also outranks `~/.ssh/config`, so `SshRemoteConfig.sshOptions` is the ONLY way a user can change one of these defaults - that is what makes an exotic transport (a tailcat / cloudflared / Teleport `ProxyCommand`, a `ProxyJump` bastion) expressible without a field per transport. `RequestTTY` is RESERVED: it is derived per command from whether the remote agent speaks stream-json, and a forced TTY corrupts that stream, so it is a property of the command and pinning it per host silently breaks agents. The `'interactive'` context drops `BatchMode`, `RequestTTY` and `LogLevel` (the user is at the keyboard and can answer a passphrase prompt, the caller passes `-t`, and SSH's own warnings are the diagnostics someone watching a terminal needs) and an override may NOT reinstate one - adding it back re-breaks the terminal it was dropped for. Do NOT hand-roll another `-o` list; the module is import-free so the CLI bundle can use it too.

In renderer-only code prefer `isWindowsPlatform()`, `isMacOSPlatform()`, `isLinuxPlatform()` in `src/renderer/utils/platformUtils.ts`. Never read `process.platform` in the renderer: the `process` polyfill (`src/renderer/public/process-shim.js`) reports the sentinel `'browser'`, and `navigator.platform` is deprecated and unreliable.

Do NOT hard-code `⌘`, `Cmd+`, `Ctrl+`, `Option`, or `Alt` in UI copy, tooltips, or setting descriptions - it renders the wrong key on the other platform. Outside the renderer (CLI, main process) use `formatShortcutKeysFor(keys, isMac)` / `formatKeyFor()` in `src/shared/shortcutKeys.ts`, which owns the key maps; the renderer file is just the platform binding over it.
- **Whether a chord may be bound at all:** `findReservedShortcutCombo(keys)` over `RESERVED_SHORTCUT_COMBOS` in `src/shared/shortcutKeys.ts`. `Cmd/Ctrl+Shift+Arrow` is the OS's select-to-end inside a text field, and a Maestro binding on one wins in every input in the app, so the user loses the native behavior with no way to tell that apart from a broken text box. It is checked at BOTH ends and the second half is the one that is easy to skip: the recorder (`ShortcutsTab`) refuses a fresh binding, and `migrateShortcuts()` in `settingsStore.ts` strips one already on disk and falls back to the bundled default. A recorder-only guard leaves anyone who already bound the chord broken forever. The table is written in terms of `Meta` and comparison collapses `Ctrl`/`Command` into it, matching `eventMatchesShortcutKeys`, so one entry covers every platform - do NOT add a separate `Ctrl` row.
- **How much of the keyboard the user has mastered:** `collectBoundShortcuts(...maps)` (denominator) and `countUsedBoundShortcuts(bound, usedIds)` (numerator) in `src/renderer/constants/keyboardMastery.ts`. Every mastery figure - the help modal's bar, the Usage Dashboard ring and its Unused Shortcuts list, the leaderboard payload, and the level-up check in `settingsStore` - runs the LIVE maps (`shortcuts`, `tabShortcuts`, `FIXED_SHORTCUTS`) through these, so they cannot disagree about the total. **A shortcut with no chord bound is excluded from both ends**: it can never be fired, so counting one in the denominator makes Keyboard Maestro unreachable forever, and listing one as "unused" tells the user to go press a chord that does not exist. The numerator is not `usedShortcuts.length` either - that list keeps ids whose binding was later cleared, which reports over 100%. Do NOT hand-roll another `Object.keys(DEFAULT_SHORTCUTS).length + ...` total; there were already two rival copies that disagreed with the surfaces rendering the number.
- **Naming the OS file manager in copy:** `getFileManagerName(platform)` / `fileManagerName()` in `src/renderer/utils/platformUtils.ts` return the bare noun (`Finder` / `Explorer` / `File Manager`), and `getRevealLabel()` / `getOpenInLabel()` are built from it. Do NOT hard-code `Finder` in a hint, tooltip, or menu label - it reads wrong on Windows, and the failure is invisible on a Mac dev machine. Same class of bug as hard-coding `⌘`.
- **Color math and contrast:** `readableTextOn()`, `isReadableOn()`, `contrastRatio()`, `relativeLuminance()`, `blendColors()`, `transparentize()`, `adjustBrightness()`, `hexToRgb()` in `src/shared/colorContrast.ts`. Whenever a foreground and its background are BOTH derived from theme colors (diagram fills, chart labels, badges, generated SVG), run the foreground through `readableTextOn(preferred, backgrounds)` so a theme whose accent sits near its text color can't paint near-identical colors on top of each other. It returns the preferred color untouched when it already clears WCAG AA and nudges the theme's own color otherwise, so nothing snaps to hard-coded black/white.
- **Agent display name:** `getAgentDisplayName()` in `src/shared/agentMetadata.ts`
- **Whether an agent is working right now (main process):** `isAgentBusy(session, processManager)` and `isAiTabProcessActive(...)` in `src/main/utils/agent-busy.ts`. **Do NOT read `session.state` or `tab.state` to answer this** - `useDebouncedPersistence` forces every session and tab back to `'idle'` before writing, so a stuck busy state cannot survive a restart and the stored record ALWAYS reads idle. Liveness has to come from what is actually running: a managed process keyed by the compound AI id (`{agentId}-ai-{tabId}`, plus the legacy bare `{agentId}-ai` for the ACTIVE tab only), OR `isSessionBusyWithCli()` for a playbook the CLI drives on that agent. Two levels because two questions get asked - `isAiTabProcessActive` is per-tab (what the web server renders as a tab's state), `isAgentBusy` is per-agent ("may I hand this agent more work?", which Group Chat delegation asks). Distinct from `checkAgentBusy()` in `src/cli/services/agent-busy.ts` despite the matching filename: the CLI is a separate process with no `ProcessManager`, so it reads the sessions JSON off disk. Pick by process, and do not import across the two.

- **Toast notifications:** `notifyToast({ color, title, message, dismissible? })` in `src/renderer/stores/notificationStore.ts`. Use for async results, errors, and persistent/dismissable messages. Same five-color design language as Center Flash: `green | yellow | orange | red | theme` (default `theme`). - **Opening a modal / dashboard by name:** `UI_SURFACES` + `resolveUiSurface()` / `resolveUiSurfaceTab()` / `describeSurfaceAccess()` in `src/shared/uiSurfaces.ts`, dispatched by `openUiSurface()` in `src/renderer/utils/openUiSurface.ts`. One registry serves `maestro-cli open <surface> [--tab]`, the main-process `open_modal` validator, and the renderer dispatcher, and it carries the discovery hints (hotkey id, command-palette text, click target) so an agent can teach the manual path while opening the pane. - **Whether a modal takes the window over:** `DESTINATION_MODALS`, `closeOtherDestinations()`, and `registerExternalDestination()` in `src/renderer/stores/modalStore.ts`. A DESTINATION is a full-window view you GO to (Settings, Usage Dashboard, Director's Notes, Symphony, Cue, Marketplace, Process Monitor, System Logs, Agent Sessions, Memory, plus the Document Graph); only one is ever open, and `openModal`/`toggleModal` evict whichever other one was up. Before this, ordering was decided by each surface's fixed rank in `MODAL_PRIORITIES` instead of by what the user just asked for: the Usage Dashboard (540) opened BEHIND Director's Notes (848), and a main-panel destination opened under any overlay changed nothing on screen - both read as a dead keystroke. A dialog that answers a question ABOUT the surface beneath it is NOT a destination and is meant to layer (confirmations, rename prompts, `cueYamlEditor`, the dashboard's per-agent detail, the Symphony agent picker). Do NOT try to fix a "wrong surface won" bug by re-ranking `MODAL_PRIORITIES` - decide membership here instead. A destination owned by another store (currently only the Document Graph in `fileExplorerStore`) joins via `registerExternalDestination()` and calls `closeOtherDestinations()` on its own way in; `modalStore` must never import that store back. `DESTINATION_SHORTCUT_IDS` in the same file is the second half of that membership question and is DERIVED from it: the window keyboard handler blocks most shortcuts while a modal is up, and consults this set to decide which hotkeys still get through. It used to be a hardcoded chord test (Alt+Cmd plus `l`/`p`/`u`/`s`), which let three destinations through and killed the rest - Director's Notes to Usage Dashboard worked because `Opt+Cmd+U` matched the chord, and the way back did nothing because `Cmd+Shift+O` did not, so switching between two full-window surfaces worked in one direction only and read as a dead key. Deriving the set from `UI_SURFACES` means adding a destination cannot silently drop it back out of the guard, and a user who REBINDS a surface keeps a working hotkey, which a chord test can never promise. Do NOT add a chord back to that guard to fix a "hotkey does nothing over an open surface" bug - give the surface a `shortcutId` in `UI_SURFACES` instead.
- **Toggling the unread filters:** `toggleTabUnreadFilter()`, `toggleAllUnreadFilters()`, and `areUnreadFiltersActive()` in `src/renderer/services/unreadFilters.ts`. The agent filter (`uiStore.showUnreadAgentsOnly`) and the tab filter (`uiStore.showUnreadOnly`) are independent state, but the tab one is NOT a plain setter: entering it saves the active AI tab in `preFilterActiveTabId` and leaving it restores that tab, so writing `setShowUnreadOnly()` directly strands the user on whatever tab the filtered view left them on. The combined toggle counts as active only when BOTH are on, so a half-filtered view COMPLETES rather than clears - "either one" would make one press turn everything off, the opposite of what a half-filtered view asks for. Everything reads the stores at call time rather than a render snapshot, because the palette entry, the keyboard shortcut, and the tab bar button fire from different render trees and a stale snapshot is the one way they disagree about direction. Do NOT inline a fourth copy of the save/restore dance.
- **Scheduled Tasks (clock-driven Cue subs):** types and pure helpers in `src/shared/cue/scheduled-tasks.ts`, filesystem work in `src/main/cue/cue-scheduled-tasks.ts`. `maestro-cli cue schedule` and the Cue modal's Scheduled Tasks tab (via `cue:*ScheduledTask*` IPC) both go through that one module, so they cannot write different YAML for the same task. - **Which pipelines belong to an agent:** `pipelinesForSession(sessionId, pipelines, graphSessions)`, plus `pipelineInvolvesSession()` and `pipelineNamesDeclaredBySession()` in `src/renderer/components/CuePipelineEditor/utils/pipelineMembership.ts`. "Belongs" has two independent senses and the Cue dashboard needs both: PARTICIPATION (an agent node bound to the session, or a command node whose `owningSessionId` is the session) and DECLARATION (the pipeline is defined in that agent's own `cue.yaml`, even when no node points back at it - a fan-out that only dispatches to other agents, or an `action: command` pipeline that is just a trigger plus a shell step). The predecessor, `getPipelineColorForAgent()`, answered a COLOR question and checked agent nodes only, which broke twice over: a command-only pipeline belonged to nobody, so the Sessions table printed a dash and "View in Graph" dropped the user into every pipeline on the machine; and because two pipelines can legitimately share a color, pairing a color list back to names dropped one and mislabeled the other. Declaration matches on `getPipelineKey(sub)` because names are the grouping key `subscriptionsToPipelines` builds with, so they equal `CuePipeline.name` exactly. Do NOT reintroduce a color-based lookup, and do NOT filter agent nodes inline at a new call site.
- **How much work happened in a group chat:** `computeGroupChatActivity(entries)` in `src/shared/groupChatActivity.ts`, fed by the per-turn measurements `src/main/group-chat/group-chat-turn-metrics.ts` stamps onto each history entry. **Never present the span between a chat's first and last message as effort** - a group chat is a ROOM, not a task, so a chat used twice a week reports hundreds of hours without anyone doing anything (a real one read `481h 34m` for about five hours of work). Working time is the UNION of the busy intervals, because participants run in PARALLEL: three agents working the same ten minutes is ten minutes of chat time, not thirty, and summing per-agent durations produces a number larger than the chat's own age. Entries written before per-turn timing existed carry no `elapsedTimeMs` and degenerate to points, so `GROUP_CHAT_ACTIVITY_STITCH_MS` treats turns closer than five minutes as one block - without it an older chat reports `0m`, which is a worse lie than the span it replaced. Turn duration is measured with `beginSleepAwareSpan()`, never a bare `Date.now()` delta. `turnsWithTokens` / `turnsWithCost` are coverage counts: render a dash rather than a zero when they are 0, since a chat whose turns reported no usage is UNKNOWN, not free. Both the Group Chat Info overlay and the HTML export call the one function, so they cannot disagree about how much work a chat did.
- **Whether an agent is drawn in the Left Bar:** `sessionMatchesFilter()` and `passesUnreadFilter()` in `src/renderer/utils/sidebarMembership.ts`. Errored agents were invisible in the unread filter for exactly this reason: four rival copies of the predicate, and only one of them knew about `state === 'error'`. The inputs are shared state (`uiStore.sessionFilter`, `uiStore.showArchivedGroupChats`) rather than local `useState` for the same reason - see [STATE-PATTERNS.md → uiStore](docs/agent-guides/STATE-PATTERNS.md#uistore). Note that `orderGroupChatsForDisplay()` drops archived chats ITSELF, so a caller that has already decided archived chats are on screen must pass `{ includeArchived: true }` rather than pre-filtering, or they are removed again on the way through.

- **Audio/video playback:** media NEVER becomes a file preview tab. `handleOpenFileTab()` (`src/renderer/hooks/tabs/internal/useFilePreviewTabHandlers.ts`) is the single choke point every open path funnels through, and it diverts playable media to `useMediaPlaybackStore.openMedia()` (or `enqueueMedia()` when the caller passes `mediaMode: 'queue'`) before a tab can be created. Any path that opens SEVERAL files must pass `mediaMode: 'queue'` for every media file after the first - see `openFilesInOrder()` in `useFileContextMenu.ts` - or each open steals the player from the one before and only the last survives. The only surface media appears on is `FloatingMediaPlayer` - there is no docked/in-panel placement, so do NOT add one. Exactly ONE player exists app-wide, owned by `MediaPlaybackHost` (`src/renderer/components/MediaPlayback/`), mounted once in `App.tsx` and never unmounted: anything rendered per-tab or per-agent is torn down on switch, and removing a media element from the document pauses it. Do NOT mount a second player to play two files at once - the single-player invariant is what makes overlapping audio impossible; `stepMediaItem()` walks the queue in open order, a finished file hands off via `advanceAfterEnded()`, and the history menu jumps by recency. **Queue and history are two lists with opposite lifetimes:** the queue persists (settings key `mediaPlayerQueue`, debounced writes, hydrated in `settingsStore`) while history is per-boot, so history holds whole `MediaItem`s rather than IDs into the queue - never "simplify" it back into pointers, or dropping a queue entry would rewrite what the user already heard. Classify media with `getOpenedMediaKind()` in `src/renderer/utils/mediaItems.ts`. **A `file://` link clicked in markdown must go through `openFileUrl()`** (`src/renderer/utils/openFileUrl.ts`), never straight to `shell.openPath`: the file-link plugins emit `file://` for any path outside the project root, so an agent mentioning `~/Scratch/x.mp3` was handing it to the OS player and bypassing the choke point entirely. **The player's height is derived, never stored** (`src/renderer/utils/mediaFloatGeometry.ts`): chrome for audio, chrome + `width / aspect` for video, where the aspect is the file's real `videoWidth / videoHeight` and the chrome is MEASURED (font metrics differ per platform, so a hard-coded transport height letterboxes video somewhere). Only position and a per-kind width persist, so a mixed queue reshapes itself as it advances. **Minimize and close are different actions and must stay that way:** the `-` button sets `dismissed` (widget hidden, audio continues, `NowPlayingIndicator` in the Left Bar header becomes its play/pause via `requestToggle` plus a separate restore button), while `x` calls `closeItem` (player released, sound stops, rest of the queue intact). Minimize is a `hidden` STYLE FLAG on `FloatingMediaPlayer`, never a different render branch in `MediaPlaybackHost` - moving the media element in the React tree unmounts it, and that runs the spec's pause steps. **Neither list shows the loaded track:** history records DEPARTURES (a track enters when it stops being active) and `historyForActiveChange` also strips the incoming id, while the queue menu filters via `upcomingMediaItems()` at display time - the active item must stay in `items` or `stepMediaItem` loses prev/next. `clearQueue` keeps the loaded track, since clearing what is queued must not stop playback. A control that hides itself must not silently stop media, and a close button that only hid it leaves audio coming from nowhere. User docs: [media-player.md](docs/media-player.md).

Keep the stored bounds and the live clamp separate - the stored bounds decide what may be written to disk, while the `maxWidth` passed to the drag folds in the container as it is right now, so a width that was legal on a maximized window can't swallow the canvas after the modal is resized down.
- **A modal default sized to the screen:** `viewportModalSize({ width, height })` in `src/renderer/utils/modalSizing.ts`, passed as `defaultSize` to `useResizableModal`. Only for surfaces the user pans around INSIDE (a graph, a dashboard) - a form or dialog has a natural width and more room buys it nothing. A fixed default that reads as generous on a laptop is a postage stamp on a 5K display, and the user re-drags it on every machine. Memoize it once per mount: the hook re-clamps the live size on `resize`, and a default that moves under it fights that listener.
- **Focus after render:** `useFocusAfterRender()` in `src/renderer/hooks/utils/useFocusAfterRender.ts` (do NOT use `useEffect + setTimeout(() => ref.focus())`). Same file: `useFocusOnMount()` for a modal that must land with its input focused, and **`useFocusOnClose(ref, isOpen)` for handing the caret BACK when a transient surface closes**. The layer stack restores focus generically now (`useLayerStack` snapshots `document.activeElement` when a focus-capturing layer registers and hands it back when the layer unregisters, but ONLY if focus landed nowhere), so a modal registered through `useModalLayer` needs nothing. Reach for `useFocusOnClose` when the surface is NOT a registered layer (an inline editor, a popover) or when the caret should land somewhere OTHER than where it started - it wins, because the stack defers to anything that already claimed focus. It fires only on the true -> false edge, so it cannot steal focus from something the user clicked afterwards. Do NOT restore focus by hand in a modal's `onClose`: a surface dismissed with Escape never runs it, which is how focus ended up on `document.body` with the pane behind it looking ready while swallowing the next keystroke.
- **Event listeners:** `useEventListener()` in `src/renderer/hooks/utils/useEventListener.ts` (do NOT pair raw `addEventListener`/`removeEventListener` inside useEffect)
- **Debounce/throttle:** `useDebouncedValue()`, `useDebouncedCallback()`, `useThrottledCallback()` in `src/renderer/hooks/utils/useThrottle.ts` (filename is misleading - all three live here)
- **Identity-stable callback:** `useStableCallback()` in `src/renderer/hooks/utils/useStableCallback.ts` - one identity forever, always calling the newest implementation. Reach for it when a new callback identity is read as a STRUCTURAL change rather than a fresh value. The canonical case is `createMarkdownComponents()`: it builds a fresh map of component functions, so rebuilding it gives React a new component TYPE for every element and it unmounts and remounts the entire rendered document, discarding the reader's scroll position and restarting images and Mermaid. Any callback that closes over document content (a task-checkbox toggle, for instance) is reborn on every edit and triggers exactly that. Do NOT use it to silence an exhaustive-deps warning - it hides the callback from dependency arrays, so an effect that should re-run when its captured values change no longer will.
- **Render markdown:** `<Markdown preset="chat | document | wizard-bubble | release-notes">` from `src/renderer/components/Markdown/` (do NOT hand-roll `<ReactMarkdown>` + a per-surface `components`/plugin map). The chat preset is what `MarkdownRenderer` wraps. Shared internals: `buildMarkdownPlugins` (`Markdown/plugins.ts`), `preprocessMarkdown` (`Markdown/preprocess.ts`), leaf renderers in `Markdown/components/*`, and the document component map `createMarkdownComponents()` in `src/renderer/utils/markdownConfig.ts`. See [UI-PATTERNS.md → `<Markdown>`](docs/agent-guides/UI-PATTERNS.md).
- **Clickable task checkboxes in rendered markdown:** `toggleTaskCheckboxAtLine(content, line)` in `src/renderer/utils/markdownTasks.ts`, plus `rehypeSourceLine` (`src/renderer/components/Markdown/rehypeSourceLine.ts`) and the `onTaskToggle` option on `createMarkdownComponents()`, which swaps in `<TaskCheckbox>`. react-markdown renders every GFM checkbox `disabled`, so those three pieces are what make one clickable - the file preview and the Auto Run panel both ride them. Do NOT count checkboxes in the DOM and map them onto the Nth `- [ ]` line: that drifts the moment a task marker appears inside a code fence. **Every component override in `createMarkdownComponents()` must forward its props** (destructure `node` out, spread the rest): `rehypeSourceLine` tags EVERY block, and `lineSync.domGetTopLineByAttr()` reads those tags to keep the file preview and the editor on the same line across the toggle. `React.createElement('p', null, children)` eats the attribute, which left HEADINGS as the only anchored blocks - so a document scrolled to the very top reported the first heading, and hitting Edit jumped there. See [UI-PATTERNS.md → Clickable task checkboxes](docs/agent-guides/UI-PATTERNS.md#clickable-task-checkboxes) and [Preview/edit scroll sync](docs/agent-guides/UI-PATTERNS.md#previewedit-scroll-sync-rides-the-same-data-source-line-tags).
- **Model/effort badges on a finished turn:** `<TurnSettingPills>` in `src/renderer/components/ui/TurnSettingPills.tsx`, fed from `LogEntry.turnModel` / `turnEffort`. Those are stamped at SEND time by `codifyTurnSettings()` in `src/renderer/utils/providerTabSessions.ts` - spread it into whatever tab patch marks the tab busy. Never label a turn from the live tab or agent value: settings are codified at send, so a model change made mid-stream must not relabel the response already running. **A QUEUED message freezes its settings when it is queued**, since the queue may not drain until several model changes later: every path that builds a `QueuedItem` spreads `captureQueuedTurnSettings()` into `item.turnSettings`, and both the pills (`markTabRunningQueuedItem`) and the spawn (`agentStore.processQueuedItem`) read it back through `codifyQueuedTurnSettings()`. The presence of the object is the capture flag - an undefined model INSIDE it means "the agent default was chosen", so never `?? ` it against the live value. See [UI-PATTERNS.md → Turn Attribution Pills](docs/agent-guides/UI-PATTERNS.md#turn-attribution-pills-turnsettingpills).
- **The tab a queued item is going to:** `resolveQueuedItemTabName(session, item)` in `src/renderer/utils/executionQueue.ts` for the LABEL, `resolveQueuedItemTarget()` in `src/renderer/utils/tabHelpers/index.ts` for the tab itself. Unlike `turnSettings`, a `QueuedItem`'s `tabName` is NOT frozen on purpose - it is a last-known fallback for a tab that is gone by the time the queue drains. Do NOT render `item.tabName` directly: an item queued into a brand-new tab snapshots `New` and keeps it forever, so after auto-naming the Execution Queue indicator grouped one tab under whichever name its FIRST item happened to carry, and the browser listed two rows for one tab under two different names. The resolver reads the live tab, then a closed-but-draining orphan, then the snapshot. See [UI-PATTERNS.md → Queued Item Tab Labels](docs/agent-guides/UI-PATTERNS.md#queued-item-tab-labels-resolvequeueditemtabname).
- **Editing the newest queued message:** `requestEditLastQueuedMessage()` in `src/renderer/services/editQueuedMessage.ts`. Two surfaces offer it (the `editLastQueuedMessage` chord and the palette's `Edit Last Queued Message`) and both route here, so they cannot drift on which item they pick, which tab they land on, or what they say when there is nothing to edit. Everything is read from the stores AT CALL TIME, never from a render snapshot - the pencil on a queued row reads live props, so a stale snapshot is the one way this can claim nothing is queued while a card sits on screen. A missing tab RANKS rather than filters (a closed tab must not turn into "nothing is queued"), only `type === 'command'` items are skipped, and the two empties are named apart: `Nothing queued to edit` vs `Only commands are queued`. See [RENDERER-SERVICES.md](docs/agent-guides/RENDERER-SERVICES.md#editqueuedmessagets---edit-the-newest-queued-message).
- **Whether a Force Send control exists at all:** `shouldOfferForceSend(eligibility)` in `src/renderer/utils/executionQueue.ts`, paired with `getForceSendEligibility()` (can it run?) and `getForceSendTitle()` (why not?). Rendering and enabling are separate questions: `canForce` decides DISABLED, this decides PRESENT. Only `needs-forced-parallel` is worth showing dimmed, because its tooltip names a setting the user can go turn on; `no-target-tab` could never work, and `target-tab-busy` resolves itself (a tab runs one turn at a time, so the item is already next in line). Both surfaces - the inline QUEUED card in `QueuedItemsList` and the Execution Queue browser's Send Now - call it, so they cannot drift on when the button appears, which they had already done once in both directions.
- **Model tier / effort level (`'low' | 'medium' | 'high'`):** `resolveTierModel()`, `resolveEffortLevel()`, `cheapTurnSettings()` in `src/shared/modelTiers.ts`; `MAESTRO:MODEL` markers via `findActiveModelHint()` in `src/shared/autorunModelHints.ts`; the join in `resolveTurnSettings()` in `src/shared/autorunTurnSettings.ts`. A marker's PLACEMENT is its scope (own line = from there down, end of a task line = that task only), the two layer per axis, and `'default'` stays a directive rather than collapsing to `undefined` so a task can opt out of a document-wide hint - do NOT normalize it away at parse time. One vocabulary maps to every provider, and it maps to ladder POSITIONS, not same-named strings - Claude's `high` is `max`, Codex's `low` is `minimal`. Do NOT pass a provider's own effort word through from a document, and do NOT add a tier table for a provider whose model IDs are discovered at runtime (codex, copilot-cli, opencode): a shipped guess rots into naming a model the user cannot run. Unmapped returns `undefined`, meaning inherit-the-agent's-value AND warn - never substitute silently, because a deep-planning task quietly running on the default model is the exact failure this replaced. Shared because the desktop and CLI Auto Run engines must resolve a document identically.
- **Auto Run markers (HITL / halt / model hint):** `scanMaestroMarkers()`, `findPendingHitlGate()`, `detectHaltMarker()`, `hasMaestroMarker()` in `src/shared/autorunMarkers.ts`, rendered by `remarkMaestroMarkers` (`src/renderer/components/Markdown/remarkMaestroMarkers.ts`) + `<MarkerPill>`. All three markers are HTML comments, so they render as NOTHING - and two of them silently block the next run (a live HITL gate pauses it, a halt marker makes Auto Run refuse to start), which presents to the user as "I pressed Run and nothing happened". `scanMaestroMarkers` is the rendering side and reports each marker's STATUS (`live` / `spent` / `invalid`), because presence is not the useful question: a gate above an unchecked task and one above a checked task are a character apart in the source and only the first stops the run. Do NOT hand-roll another marker regex - the engines and the pill must agree, or the pill sends the user to remove the wrong marker. Pills are wired ONLY into `createMarkdownComponents` (the document map); chat builds its own map, so an agent explaining the syntax in a message keeps rendering as prose rather than claiming a setting exists. One deliberate asymmetry: `detectHaltMarker` is NOT fence-aware (the engine must never miss a halt an agent mis-indented) while `scanMaestroMarkers` is (a pill on a documentation example would be a lie).
- **Fence-aware markdown scanning:** `forEachMarkdownLine()`, `UNCHECKED_TASK_REGEX`, `CHECKED_TASK_COUNT_REGEX`, `CHECKED_TASK_REGEX` in `src/shared/markdownTaskScan.ts`. Every Auto Run document scanner (task counting, HITL gates, model hints, human-step detection) rides this one walk, in `shared/` because the CLI engine cannot import from `src/renderer`. Do NOT hand-roll another line loop: any scanner that forgets the fence bookkeeping fires on a playbook that merely DOCUMENTS the marker syntax, and the copies drift on closing-fence length, tilde fences, and CRLF.
- **Thinking mode (`'off' | 'on' | 'sticky'`):** `THINKING_MODES`, `nextThinkingMode()`, `asThinkingMode()` in `src/shared/types.ts`. One cycle order serves the composer's Thinking chip and `maestro-cli tab thinking <tab-id> cycle`, so a click and a CLI cycle cannot disagree about what comes next - do NOT hand-roll another `['off', 'on', 'sticky']` ladder or an inline `indexOf(...) + 1` step. Narrow anything arriving from the CLI or the web bridge through `asThinkingMode()` rather than casting: `'off'` is a truthy string, and an unrecognized mode written straight into a tab is a permanently wrong chip rather than a rejected command.
