# Canonical Utilities - Full Rationale

The complete, reasoned entry for every commonly-reimplemented function in the codebase. The always-loaded index in [CLAUDE.md](../../CLAUDE.md#commonly-reimplemented-functions-do-not-add-new-copies) lists each entry as one line (name, canonical symbols, path); this file carries the why - the failure each canonical implementation replaced, the invariants it protects, and the traps that made the duplicates subtly wrong. Read the matching entry here BEFORE extending or working around one of these utilities.

Grep-verified 2026-09-04 (`npm run docs:verify` checks that every path below still resolves).

- **ID generation:** `generateId()` in `src/renderer/utils/ids.ts`, `generateUUID()` in `src/shared/uuid.ts`
- **Format file size:** `formatSize()` in `src/shared/formatters.ts`
- **Format numbers:** `formatNumber()` (compact: `1.2M`) and `formatCount()` (exact, grouped: `1,204,993`) in `src/shared/formatters.ts`. Pick by whether the digits ARE the information - a badge wants the magnitude, a filtered row count wants the number.
- **Format tokens:** `formatTokens()`, `formatTokensCompact()`, `estimateTokenCount()` in `src/shared/formatters.ts`
- **Format elapsed time:** `formatElapsedTimeColon()` in `src/shared/formatters.ts`
- **Humanized durations:** everything in `src/shared/duration.ts` (re-exported from `formatters.ts`). `humanizeDuration(ms, opts)` is the one engine; `formatDurationHuman` / `Compact` / `Verbose` / `Parts` / `Decimal` / `Long` / `Words`, plus `formatActiveTime`, `formatElapsedTime`, and `formatTurnDuration` (transcript turn time: day-capped, second-free, `<1m` below a minute), are presets over it. **Never hand-roll another `Math.floor(ms / 86400000)` ladder** - a dozen near-identical copies had already drifted apart on where the ladder stops, whether a zero segment is padded (`"2h 0m"` vs `"2h"`), and whether a countdown rounds up. Those are options (`units`, `maxUnits`, `style`, `keepZeroUnits`, `adjacentUnits`, `round`, `fallback`), so pick a preset or call the engine. Unit sizes are in `DURATION_MS` - don't redeclare `const DAY = 86400000`. See [SHARED-UTILS.md → Durations](docs/agent-guides/SHARED-UTILS.md#durations-srcshareddurationts---both).
- **Format profiling spans (ms):** `formatDuration()` in `src/shared/performance-metrics.ts` (NOT formatters.ts - common mistake). Two-decimal `"123.45ms"` / `"1.23s"` for perf traces only; it caps at seconds, so a multi-day span comes out as a giant seconds float. For anything user-facing use `src/shared/duration.ts`.
- **Format relative time:** `formatRelativeTime()` in `src/shared/formatters.ts`
- **Format cost:** `formatCost()` in `src/shared/formatters.ts`
- **Timestamp for a generated file name:** `fileTimestampSlug(dateOrTimestamp?)` in `src/shared/formatters.ts` - `20260713-142530`, filesystem-safe everywhere and chronologically sortable. LOCAL time on purpose: the name is read by the human who pasted the image at that wall-clock moment, so a UTC stamp reads as the wrong hour to everyone outside UTC. Both the renderer's `saveImageToProject()` and the CLI's `image save` name files with it, so a screenshot saved by hand and the same one saved by an agent cannot come out under two different conventions.
- **Summing a Codex session's tokens:** `CodexTokenCounts` in `src/shared/codexTokenUsage.ts`. Codex reports usage in two shapes and only one is per-turn: `turn.completed.usage` and `info.last_token_usage` are that turn's numbers, while `info.total_token_usage` on a `token_count` event is the running SESSION TOTAL. Summing the total across events is the trap - a session with N turns reports 1+2+...+N times its real tokens, so cost grows with the SQUARE of the conversation length, which is what turned 1.7B input tokens into 75B and let Codex outrank Claude on a dashboard driven almost entirely by Claude agents. The accumulator prefers `last_token_usage`, falls back to a cumulative DELTA, and reads a total that moves backwards as a counter restart (a resume or fork) rather than clamping it to zero. Reasoning output folds into `outputTokens`; `cachedTokens` stays a SUBSET of `inputTokens`. All three transcript scanners go through it so they cannot disagree again - do NOT hand-roll a fourth sum. It has no Electron imports so the CLI can bundle it. **Bump `CODEX_SESSION_CACHE_VERSION` in `src/main/storage/codex-session-storage.ts` whenever this math changes**: entries are reused while `fileMtimeMs` still covers the file, and a parsing fix does not touch a transcript's mtime, so old inflated numbers are served until a session is rewritten.
- **Capping stored tool output:** `MAX_PERSISTED_TOOL_OUTPUT_CHARS`, `compactToolOutput()` and `compactSessionToolOutputs()` in `src/shared/toolOutput.ts`. A tool result is transcript evidence, but it is also copied into the renderer store, `maestro-sessions.json`, and the entire `sessions:getAll` web bootstrap. One Antigravity command stored a 67MB one-line result, which grew the bootstrap frame to 126MB and made iOS appear disconnected while it parsed the same Maestro instance. Cap at parser ingestion to stop new growth, at renderer persistence for every provider, and on main-process load to heal old files before any browser receives them. Short values retain their original type; oversized objects become a JSON preview because preserving a large object defeats the cap. Do not add another provider-specific limit or remove the load migration: historical sessions survive parser fixes until a storage boundary rewrites them.
- **Path utilities:** `truncatePath()`, `getParentDir()`, `truncateCommand()`, `isAbsolutePath()`, `getBasename()` in `src/shared/formatters.ts`
- **Reading a zip from disk:** `readZipArchive(filePath, options?)`, `extractZipTo()`, `isUnsafeZipEntryName()` in `src/main/utils/zip-archive.ts`. Playbook import, Cue backup inspect/restore, and the debug-package tests only need entry names and bytes. The previous reader was `adm-zip`, whose `extractAllTo(..., overwrite)` follows a destination symlink (GHSA-vwc7-r8mq-g2x9) and has no patched release. A wrapper around that API cannot close Dependabot, and `npm audit fix --force` would downgrade to 0.5.8 and re-open the zip-bomb advisory fixed in 0.6.0. `unzipSync` inflates every selected entry, so a caller that only needs `manifest.json` must pass `names` or `filter` (Cue list/inspect do). Default caps on entry count and aggregate `originalSize` refuse a zip bomb before the bytes sit in the main process. `extractZipTo` refuses `..` / absolute names, refuses to overwrite a dest that is already a symlink, and walks every existing path component under the dest root so an intermediate symlink cannot escape. Do NOT add a second unzip helper in a handler or test; `analyze-perf-trace.mjs` is the one exception (it cannot import compiled main-process code) and it still uses `fflate.unzipSync` rather than extract-to-disk.
- **Referencing / thumbnailing a pasted transcript image:** `IMAGE_REF_PREFIX`, `isSessionImageRef()`, `sessionImageThumbnailSrc(ref, maxW, maxH)` in `src/shared/sessionImageRefs.ts`. Pasted images are relocated out of `maestro-sessions.json` into a content-addressed store and referenced as `maestro-image://store/<sha256>.<ext>` (see `src/main/storage/session-image-store.ts`). The prefix used to be a bare `'maestro-image://'` literal repeated across the store, `clipboard.ts`, `imageExport.ts`, and the transcript; it lives here so main and renderer share ONE definition and so the renderer can build a URL without importing fs-dependent main-process code. `sessionImageThumbnailSrc` appends the `?tw=&th=` query that the `maestro-image` protocol handler reads to serve a disk-cached downscaled rendition (`src/main/storage/session-image-thumbnails.ts`). Use it for ANY fixed-size chip: a transcript screenshot is routinely 4984x2578 / 13MB, and Chromium has no way to decode "just the small version" - it decodes the full 12-megapixel bitmap (~48MB RGBA, ~70ms) to paint a 200x80 chip. A field trace of one tab found 47 images totalling 193 megapixels (~0.7GB decoded) thrashing the decode cache on every scroll pass. A BARE ref (no query) must keep serving the original bytes - the lightbox, clipboard copy, and every export path depend on it - so `resolveToFilePath` strips the query rather than treating it as part of the basename, and the traversal guard still runs on the stripped basename. Pair it with `loading="lazy"` + `decoding="async"` on the `<img>`; the thumbnail is what makes the decode cheap, lazy is what stops off-screen work entirely.
- **Serializing async work on one entity:** `createKeyedWriteQueue()` in `src/shared/keyedWriteQueue.ts`, re-exported from `src/main/utils/atomic-json-store.ts` so all seven main-process call sites keep their existing import. Each key (a session id, a `${sessionId}:${tabId}` pair) gets its own promise chain: callers mutating the same entity run strictly one at a time while different keys stay concurrent, and the chain continues past a rejection so one failed write cannot strand every later write for that key. Settled entries are deleted from the backing Map, which is what keeps it bounded in a process that runs for days. It lives in `shared/` rather than beside `atomicWriteJson` because BOTH processes need it and the renderer cannot import a module that pulls in `fs/promises` - the same hoist, for the same reason, as `assertSerializedJsonIsSafe` in `src/shared/jsonUtils.ts`.

  **A queue held in one process cannot order work performed in another.** A remote tab rename is therefore ordered twice, and the two queues answer different questions: the one in `src/main/web-server/callbacks/tabCallbacks.ts` orders the PROTOCOL - it is what puts `rename_tab_result` frames back on the wire in request order - while the one in `src/renderer/hooks/remote/useRemoteIntegration.ts` orders the WORK, which is where a rename actually happens (provider metadata write, history relabel, store patch). The server's queue deliberately stops waiting after `RENAME_CONFIRMATION_RELEASE_MS`, so an unresponsive renderer cannot wedge a tab; at that moment it frees the slot and dispatches the next rename while the abandoned one may still be running in the renderer. Those two then overlap and the older one can finish last, overwriting the newer name in both the provider metadata and the store - the exact lost update the queue was added to prevent, reopened past the release window. Both queues key on `${sessionId}:${tabId}`, so ordering is per tab and a rename never becomes an app-wide lock.

  Three rules for a renderer-side queue. It must be at MODULE scope, never a ref: the listener is registered from an effect that can re-run, and a queue rebuilt on re-registration forgets the work still in flight (`group-chat-storage.ts` holds its own at module scope for the same reason). Its slot must be handed on after a bounded budget as well as on settle, because `ipcRenderer.invoke` never times out - a main-process handler that never returns leaves its promise pending for the life of the window, and every later rename for that tab would sit behind it unattempted. And handing the slot on early is not cancellation: an in-flight IPC cannot be recalled, so the writer re-reads the newest REQUESTED name when its own write lands and writes once more if it was superseded, which is what turns a stale write that lands late into a self-correcting one instead of the final word. Do NOT hand-roll another `Map<string, Promise<void>>` chain.

- **Loading an image for canvas compositing:** `loadImageElement(src)` in `src/renderer/utils/loadImage.ts`. Wraps `new Image()` + `onload` / `onerror` in a promise and REJECTS on failure, so a caller can never draw a half-decoded element and report success. `compositeAnnotatedImage` and `cropImageDataUrl` both use it, which is what keeps a crop and the save that follows it from disagreeing about whether the source loaded. Accepts anything an `<img src>` accepts, including `maestro-image://` store refs, and the resolved element is decoded so `naturalWidth` / `naturalHeight` are safe to read immediately. Two other loaders in the renderer look like duplicates and are NOT - do not "consolidate" them without reading why: `loadImage()` in `AchievementShareButton.tsx` resolves `null` on purpose (a missing avatar or GitHub logo falls back to a drawn placeholder rather than failing the whole share card), and `svgToPngDataUrl()` in `imageExport.ts` sets `img.decoding = 'async'` before assigning `src`, a hint this helper does not expose. Reach for `loadImageElement` when a failed load must abort the operation.

- **Classifying a file by extension:** `getFileCategory()`, `isPreviewableFile()`, `matchesFileCategory()`, `getFileExtension()` in `src/shared/fileCategories.ts`. One table answers both "can Maestro open this?" and "which bucket is it in?" - `isPreviewableFile` is DERIVED from `getFileCategory`, so a file cannot show up under a filter pill and then refuse to open, nor be openable while invisible under every pill. Audio and video are NOT listed there; they resolve through `getMediaKind()` in `mediaTypes.ts`, which is the single source of truth for what Chromium can decode. Do NOT hand-roll another `TEXT_EXTENSIONS` set - the private copies inside `FileSearchModal` are exactly what this replaced. Distinct from the sets in `src/renderer/utils/fileExplorerIcons/shared.ts`, which exist to pick an ICON and split far more finely (lockfiles, test folders); pick by question and do not merge them.
- **Guarding a serialized JSON payload before it overwrites a file:** `assertSerializedJsonIsSafe(serialized, target)` in `src/shared/jsonUtils.ts`. The failure it exists to stop is `JSON.stringify` returning `undefined` - which it does for `undefined`, a function, or a symbol - because `writeFile` then persists the literal text `"undefined"`: unparseable, and a silent way to clobber a good store. The empty string is rejected for the same reason. It does NOT unconditionally round-trip parse. Beyond the `undefined` case `JSON.stringify` cannot produce malformed JSON (a circular reference throws instead of emitting something broken), so the parse only ever catches truncation, and a string still in memory cannot be truncated. Above 1MB it therefore falls back to a balanced-delimiter check on the first and last non-whitespace characters. That matters because the check is paid on the write path: on the 20MB agent-runs store the re-parse alone cost ~40ms per write, on the Electron main thread, which is the same thread that answers every IPC call - and a field trace attributed 82% of active main-process CPU to synchronous JSON work of exactly this shape. Two rival copies existed before this was hoisted: a private `assertSerializedJsonIsSafe` in `src/main/utils/atomic-json-store.ts` and a bare, unexplained `JSON.parse(content)` inline in `atomicWriteJson` in `src/cli/services/agent-run-store.ts`. Do NOT add a third, and do NOT "harden" it back into an unconditional parse - the large-payload branch is the whole point, not an oversight. The trailing-whitespace tolerance is load-bearing too: the agent-run store appends a newline to every file it writes.
- **Strip ANSI / collapse progress overwrites:** `stripAnsiCodes()`, `processCarriageReturns()` in `src/shared/stringUtils.ts`
- **Reading what a TUI painted, not just its bytes:** `replayTerminalScreen(raw)`, `capturedAlternateScreen(raw)` in `src/maestro-p/screen-replay.ts`. A diffing renderer (Claude Code's alternate-screen UI) rewrites only the cells that changed and jumps the cursor over the rest, so `stripAnsiCodes` on a captured stream loses text that is still on screen: the `/usage` scrape read the second weekly header as a bare `Fable)` and reported that bar as 0%. Replay puts every cell where the terminal drew it. Strip is right for line-oriented output you only need clean; replay is right whenever the capture is cursor-addressed. It deliberately has no wrapping or scrolling, so it needs no PTY size, and it returns the LAST alternate screen even after the TUI switched back out of it.
- **Shell escape:** `shellEscape()`, `shellEscapeArgs()`, `shellEscapeForDoubleQuotes()` in `src/main/utils/shell-escape.ts`
- **A path handed to a REMOTE shell (`cd`, `ls`, `stat` over SSH):** `shellEscapeRemotePath()` in `src/main/utils/shell-escape.ts`. `shellEscape()` single-quotes, and a single-quoted `'~/proj'` never expands: the remote looks for a directory literally named `~`, and nothing local can substitute the remote user's home (`expandTilde()` produced `/Users/<local>/git-projects`, which validated green and then did not exist on the host). A leading `~` or `$HOME` is rendered as `"$HOME/rest"`; every other path falls through to `shellEscape()` byte for byte. Every remote `cd` rides it - both SSH command builders, the terminal tab handler, `SshCommandRunner`, and all of `remote-fs.ts` - because four private copies of the rule had already drifted, and one of them defaulted to a quoted `'~'` that could not work. Do NOT hand-roll another `startsWith('~/')` branch at a new call site.
- **SSH connection options (`ssh -o`):** `resolveSshOptions()` / `buildSshOptionArgs()` / `validateSshOption()` in `src/shared/sshOptions.ts`. FOUR sites used to build this list by hand - the agent spawn builder, the Test Connection probe, `SshCommandRunner`, and the interactive terminal tab in `ipc/handlers/process.ts` - and they had already drifted: only one set `LogLevel`, and the terminal path omitted `BatchMode` entirely, so a remote could test green and then connect with a different option set when an agent actually ran on it. The merge is CASE-INSENSITIVE, which is the whole reason it is one function: OpenSSH treats keywords case-insensitively but applies `-o` FIRST-WINS, so a naive spread emitting both `-o ConnectTimeout=10` and `-o connecttimeout=45` silently keeps the 10 and the user's override does nothing. A command-line `-o` also outranks `~/.ssh/config`, so `SshRemoteConfig.sshOptions` is the ONLY way a user can change one of these defaults - that is what makes an exotic transport (a tailcat / cloudflared / Teleport `ProxyCommand`, a `ProxyJump` bastion) expressible without a field per transport. `RequestTTY` is RESERVED: it is derived per command from whether the remote agent speaks stream-json, and a forced TTY corrupts that stream, so it is a property of the command and pinning it per host silently breaks agents. The `'interactive'` context drops `BatchMode`, `RequestTTY` and `LogLevel` (the user is at the keyboard and can answer a passphrase prompt, the caller passes `-t`, and SSH's own warnings are the diagnostics someone watching a terminal needs) and an override may NOT reinstate one - adding it back re-breaks the terminal it was dropped for. Do NOT hand-roll another `-o` list; the module is import-free so the CLI bundle can use it too.
- **Platform detection:** `isWindows()`, `isMacOS()`, `isLinux()` in `src/shared/platformDetection.ts` (works in both processes). In renderer-only code prefer `isWindowsPlatform()`, `isMacOSPlatform()`, `isLinuxPlatform()` in `src/renderer/utils/platformUtils.ts`. Never read `process.platform` in the renderer: the `process` polyfill (`src/renderer/public/process-shim.js`) reports the sentinel `'browser'`, and `navigator.platform` is deprecated and unreliable.
- **Whether a working directory can be spawned into:** `unusableCwdReason(cwd)` in `src/main/process-manager/utils/spawnCwd.ts`, called once by `ProcessManager.spawn()` for both the PTY and child-process paths. A missing `cwd` is an ordinary user state (a deleted worktree, an unmounted volume, a renamed project folder) and it MUST be caught before the spawn, because node-pty's Windows path does not fail anywhere catchable: `pty.spawn()` returns a live-looking object and defers the real work to `WindowsPtyAgent._completePtyConnection()`, which runs later from the conout worker's `onReady` callback (or a 5 s timeout) and calls the native `conptyNative.connect(pty, commandLine, cwd, ...)` there. A `cwd` that is not a directory throws win32 `error 267` (ERROR_DIRECTORY) out of THAT callback - past the `try`/`catch` in `PtySpawner.spawn`, past the IPC handler, into the uncaught-exception handler - while the spawn is reported as successful and the pty is left a zombie with no inner pid, so the caller asks again. Sentry grouped 998 of these crashes under one issue (MAESTRO-S0), 995 of them from a single installation relaunching into the same missing directory. The spawn is REFUSED rather than redirected to the home directory: an agent silently pointed at the wrong tree would read and edit files nobody asked it to. The check is deliberately conservative and only reports a directory it can PROVE is unusable (`ENOENT`/`ENOTDIR`, or a path that stats as a non-directory); any other stat failure returns `null` and lets the spawn proceed, so a locked folder or a flaky network mount can never lock a user out of starting their agent. The refusal emits an `agent-error` naming the directory, so it reaches the user instead of only the log.
- **Modifier-key display text:** `formatKey()`, `formatShortcutKeys()`, `formatMetaKey()` (symbol: `⌘` / `Ctrl`), `formatMetaKeyName()` (prose: `Command` / `Ctrl`), `formatAltKeyName()` (prose: `Option` / `Alt`) in `src/renderer/utils/shortcutFormatter.ts`. Do NOT hard-code `⌘`, `Cmd+`, `Ctrl+`, `Option`, or `Alt` in UI copy, tooltips, or setting descriptions - it renders the wrong key on the other platform. Outside the renderer (CLI, main process) use `formatShortcutKeysFor(keys, isMac)` / `formatKeyFor()` in `src/shared/shortcutKeys.ts`, which owns the key maps; the renderer file is just the platform binding over it.
- **Advertising a shortcut next to the control that fires it:** `ShortcutHint` (`variant="chip"` for an inline key-cap, `variant="row"` for a hint header pinned above a dropdown's option list) and `shortcutSuffix(keys)` (for a `title=` tooltip) in `src/renderer/components/ui/ShortcutHint.tsx`. Maestro is keyboard-first, so every clickable route to an action that ALSO has a chord should show that chord where the user is already looking; this is the one component that draws it. Four byte-identical local `ShortcutHint` definitions had accumulated across the tab-bar components before it was extracted. Two invariants: read the chord from the LIVE shortcut map (`useSettingsStore(s => s.shortcuts)` / `s.tabShortcuts`) rather than spelling a default combo into the string, or a user who rebinds sees our chord instead of theirs; and both helpers render NOTHING for an empty or missing `keys`, because an action can ship unbound and a blank key-cap advertises a combo that does nothing. When a row already has a right-aligned badge, wrap the badge and the key-cap in ONE `ml-auto` container - two auto margins on siblings split the free space and strand the badge mid-row.
- **Whether a chord may be bound at all:** `findReservedShortcutCombo(keys)` over `RESERVED_SHORTCUT_COMBOS` in `src/shared/shortcutKeys.ts`. `Cmd/Ctrl+Shift+Arrow` is the OS's select-to-end inside a text field, and a Maestro binding on one wins in every input in the app, so the user loses the native behavior with no way to tell that apart from a broken text box. It is checked at BOTH ends and the second half is the one that is easy to skip: the recorder (`ShortcutsTab`) refuses a fresh binding, and `migrateShortcuts()` in `settingsStore.ts` strips one already on disk and falls back to the bundled default. A recorder-only guard leaves anyone who already bound the chord broken forever. The table is written in terms of `Meta` and comparison collapses `Ctrl`/`Command` into it, matching `eventMatchesShortcutKeys`, so one entry covers every platform - do NOT add a separate `Ctrl` row.
- **Whether a keystroke belongs to a text field (guard before `preventDefault`):** `isTextInputTarget(target)` and `isTextEntryTarget(target)` in `src/renderer/utils/messageScrollNavigation.ts`; `isEditingTextTarget(target)` / `isEditingTextFocused(doc?)` in `src/renderer/utils/editableTarget.ts`. A surface-level key handler that fires while the caret is in an input steals the keystroke from whatever the user is typing, and the bug reads as the app randomly misbehaving rather than as a shortcut conflict - a bare Enter in the markdown editor also opened the file tree's selected row, because the Files tab held the app's `activeFocus` while the DOM focus was elsewhere. `activeFocus` is APP state and DOM focus is the real thing; when they disagree, real focus wins. Pick by what the key is: **`isTextInputTarget`** counts every `<input>`, `<textarea>`, and contenteditable - use it for arrow keys and Enter, where a range slider legitimately owns Left/Right. **`isTextEntryTarget`** is narrower, counting only inputs that swallow typed characters, so a focused slider or checkbox cannot silently disable `Cmd+Z` or a single-letter tool key. **`isEditingTextTarget`** asks the same question by instance rather than `tagName` (so it sees an `<input>` from another document/realm), and `isEditingTextFocused()` asks it of `document.activeElement` for handlers bound to `window` where the event target is `<body>`. Do NOT hand-roll another `tagName === 'INPUT' || ... || isContentEditable` chain: there are already ~8 inline copies across the renderer (`useKeyboardNavigation`, `DocumentGraphView`, `usePipelineKeyboard`, `MediaViewer`, and others) and they have drifted - some miss contenteditable, `MediaViewer`'s misses `<textarea>` entirely. Import one of these instead; see [DEDUP-TRACKER.md](DEDUP-TRACKER.md).
- **How much of the keyboard the user has mastered:** `collectBoundShortcuts(...maps)` (denominator) and `countUsedBoundShortcuts(bound, usedIds)` (numerator) in `src/renderer/constants/keyboardMastery.ts`. Every mastery figure - the help modal's bar, the Usage Dashboard ring and its Unused Shortcuts list, the leaderboard payload, and the level-up check in `settingsStore` - runs the LIVE maps (`shortcuts`, `tabShortcuts`, `FIXED_SHORTCUTS`) through these, so they cannot disagree about the total. **A shortcut with no chord bound is excluded from both ends**: it can never be fired, so counting one in the denominator makes Keyboard Maestro unreachable forever, and listing one as "unused" tells the user to go press a chord that does not exist. The numerator is not `usedShortcuts.length` either - that list keeps ids whose binding was later cleared, which reports over 100%. Do NOT hand-roll another `Object.keys(DEFAULT_SHORTCUTS).length + ...` total; there were already two rival copies that disagreed with the surfaces rendering the number.
- **Naming the OS file manager in copy:** `getFileManagerName(platform)` / `fileManagerName()` in `src/renderer/utils/platformUtils.ts` return the bare noun (`Finder` / `Explorer` / `File Manager`), and `getRevealLabel()` / `getOpenInLabel()` are built from it. Do NOT hard-code `Finder` in a hint, tooltip, or menu label - it reads wrong on Windows, and the failure is invisible on a Mac dev machine. Same class of bug as hard-coding `⌘`.
- **Color math and contrast:** `readableTextOn()`, `isReadableOn()`, `contrastRatio()`, `relativeLuminance()`, `blendColors()`, `transparentize()`, `adjustBrightness()`, `hexToRgb()` in `src/shared/colorContrast.ts`. Whenever a foreground and its background are BOTH derived from theme colors (diagram fills, chart labels, badges, generated SVG), run the foreground through `readableTextOn(preferred, backgrounds)` so a theme whose accent sits near its text color can't paint near-identical colors on top of each other. It returns the preferred color untouched when it already clears WCAG AA and nudges the theme's own color otherwise, so nothing snaps to hard-coded black/white.
- **Agent display name:** `getAgentDisplayName()` in `src/shared/agentMetadata.ts`
- **Whether an agent is working right now (main process):** `isAgentBusy(session, processManager)` and `isAiTabProcessActive(...)` in `src/main/utils/agent-busy.ts`. **Do NOT read `session.state` or `tab.state` to answer this** - `useDebouncedPersistence` forces every session and tab back to `'idle'` before writing, so a stuck busy state cannot survive a restart and the stored record ALWAYS reads idle. Liveness has to come from what is actually running: a managed process keyed by the compound AI id (`{agentId}-ai-{tabId}`, plus the legacy bare `{agentId}-ai` for the ACTIVE tab only), OR `isSessionBusyWithCli()` for a playbook the CLI drives on that agent. Two levels because two questions get asked - `isAiTabProcessActive` is per-tab (what the web server renders as a tab's state), `isAgentBusy` is per-agent ("may I hand this agent more work?", which Group Chat delegation asks). Distinct from `checkAgentBusy()` in `src/cli/services/agent-busy.ts` despite the matching filename: the CLI is a separate process with no `ProcessManager`, so it reads the sessions JSON off disk. Pick by process, and do not import across the two.
- **Which provider account an agent runs as:** `resolveAgentAccountKey(toolType, env, homeDir)`, `providerProfileKey()` / `parseProviderProfileKey()`, and `providerProfileLabel()` / `providerProfileShortLabel()` in `src/shared/providerProfiles.ts`, with the renderer-side per-agent index in `useProviderProfiles(sessions)` (`src/renderer/hooks/stats/useProviderProfiles.ts`). `toolType` alone stops being the identity the moment a second account is in play: three Claude agents can be three plans with three quota buckets, and only `CLAUDE_CONFIG_DIR` (or `CODEX_HOME`) separates them. `PROVIDER_PROFILE_CONFIGS` is the ONE place that says which providers split by account and what env var does it - the quota panels used to carry their own copy of the pair, which is how a badge's count and a filter's count get to disagree. The effective env is `effectiveAgentCustomEnvVars(sessionEnv, providerEnv)`: the session's own `customEnvVars` REPLACE the agent-level set, they do not layer over it, matching `applyAgentConfigOverrides()` and the CLI's `resolveAgentOverrides()` (a layered merge filed an agent that set only `ANTHROPIC_API_KEY` under a provider-level config dir its process never sees). - **Filtering the Git Log:** `gitLogSearchTerms(query)` and `matchesGitLogTerms(commit, terms)` in `src/renderer/utils/gitLogSearch.ts`, plus `contractGitGraphNodes(nodes, keep)` in `src/renderer/utils/gitGraphLayout.ts`. Four rules make it safe. **Fire it AFTER the content exists** - `runShellCommand` appends the card first, or the transcript scrolls to a bottom that does not include it yet. **Fire it ONCE per run, at the top**, never per output chunk: from there the transcript's own follow-the-tail handles the stream, and a scroll up mid-run pauses it as usual - a per-chunk request would pin the user to the bottom and make the transcript unreadable while a chatty command runs. **The receiver reuses the hook's own `scrollToBottomAndResume()`**, the same path the scroll-to-bottom button takes, which flips `userScrolledAwayRef` / `isAtBottomRef` BEFORE the `setState` calls - the MutationObserver reads the live refs in the same frame and would otherwise stall on the first mutation after the jump. **The detail names its session AND tab**, and a mismatch is ignored, so a command dispatched into a background tab cannot yank the view off what the user is reading. Do NOT reach for this to force ordinary agent output into view - the pause exists precisely to stop that.

- **Swipe down to close a modal on a phone:** `useLayerSwipeDismiss()` in `src/renderer/hooks/ui/useLayerSwipeDismiss.ts`, mounted once in `LayerStackProvider` (`src/renderer/contexts/LayerStackContext.tsx`). Every modal has a keyboard exit and is supposed to have a graphical one, but on a phone the first does not exist and the second has failed in practice: a header that overflows a 390px screen pushes its close pill off the right edge, and the user's only way out was to reload the page. This is the safety net, wired to `closeTopLayer()` - the same path Escape takes, so dirty-state confirmation and nested layers behave identically. It is deliberately conservative so it cannot fire by accident: web-desktop with a coarse pointer only; only while a layer is open; the gesture must START in the top quarter of the viewport (where a full-screen modal's header lives; lower down is scrolling); not from a form control; not inside a region that is already scrolled down (pulling a list back toward its top is a scroll, and iOS sheets follow the same rule); and it must travel at least 80px, mostly vertically, within half a second. A surface that pans on drag (a canvas, a graph) opts out with `data-no-swipe-dismiss` on its root. Do NOT add per-modal swipe handlers - one gesture, one place, one rule.
- **Clearing the iOS status bar in a home-screen web app:** `--maestro-top-inset` (`src/renderer/index.css`, "Home-screen web apps on iOS" block) and `installStandaloneStatusBarInset()` / `measureStandaloneStatusBarInset()` in `src/renderer/utils/standaloneStatusBar.ts`. The failure it replaced: the Main Panel header rendered inside the iOS 26 status bar band, where the system draws a frosted layer and swallows taps, so the hamburger was unreachable; and the shell was clipped at the status-bar line because the roots were `height: 100%` (the small viewport) while the shell was `100dvh`. Invariants: the property is `max(env(safe-area-inset-top), var(--maestro-status-bar-inset))` because WebKit bug 301994 reports `env()` as 0 and shortens the viewport instead, and the measured half is `screen.height - innerHeight` only for `navigator.standalone === true`, portrait, and a difference under 80px (a keyboard is larger; landscape hides the bar). Traps: `display-mode: standalone` also matches Android PWAs, whose page never extends under the bar; a hard-coded 62px is wrong on every other iPhone and on a healthy WebKit; and every fixed full-screen surface (drawers, phone modals) needs the inset too because it sits outside the shell's padding. The same installer publishes a second property, `--maestro-viewport-height`, from `measureVisibleViewportHeight()`: `visualViewport.height` when the browser reports one, `innerHeight` otherwise, rounded DOWN so a fractional height cannot push a modal's footer off the bottom edge. It exists because on iOS the on-screen keyboard slides OVER the layout viewport rather than shrinking it, so `100dvh` is unchanged while the bottom ~45% of the screen is covered - a full-screen phone modal sized to `100dvh` keeps its full height with its lower half behind the keys. The failure that surfaced it: both search surfaces autofocused their input on open, so the keyboard was up from the first frame and the results list was born buried, which reads as "I can filter but I can't scroll the list." The fix is two-sided and a phone surface with a list plus a filter box needs both halves - size the sheet to `var(--maestro-viewport-height, 100dvh)`, and gate the mount focus on `usePhoneLayout()` (`useFocusAfterRender(ref, !phone)` / `useFocusOnMount(ref, undefined, !phone)`). Do NOT drop the `100dvh` fallback: a browser without `visualViewport` would otherwise get a zero-height modal.
- **Marking an agent's own hand-off in its transcript:** `readCallerIdentity()`, `buildCallerIdentityEnv()`, `callerMessageFields()`, `readCallerMessageFields()`, `isSelfDispatch()` in `src/shared/agentDelegation.ts`; `noteDispatchDelegation()` in `src/main/web-server/handlers/messageHandlers/agentDelegation.ts`; `recordAgentDelegation()` / `settleAgentDelegation()` in `src/renderer/services/agentDelegation.ts`, drawn by `<AgentDelegationCard>` from `LogEntry.delegation`. The failure it replaced: a typed `@mention` shows who was consulted through its reply's attribution header, but an agent that ran `maestro-cli dispatch` or `ask` itself left only a command line inside a tool card. A mention that does not resolve to a known agent is plain text, so the source agent delegates by hand and the same intent was visible one way and buried the other. Invariants: every agent spawn stamps `MAESTRO_CALLER_AGENT_ID` / `MAESTRO_CALLER_TAB_ID` into `effectiveCustomEnvVars` in `handle-spawn.ts` (the session layer, so it survives `STRIPPED_ENV_VARS`, which kills a stale copy inherited from whatever launched Maestro); the CLI forwards them as `fromSessionId` / `fromTabId`, the same wire names `cross_agent_ask` already used; a dispatch pill is recorded only AFTER the renderer accepted the prompt, routed to the CALLER's window; an `ask` records its own pill in `runCrossAgentAsk` as `pending` and settles it when the consult ends, because only the renderer learns the outcome. Traps: do NOT reuse `MAESTRO_AGENT_ID`, which tells `maestro-cli pianola watch` it IS Pianola and switches on its judgment handoff; a named source tab that has closed gets NO pill rather than a guessed tab (the fallback to a lone busy tab, then the active tab, is only for a shell with no tab stamp); and a dispatch into the caller's own tab (or its agent's active tab, with no tab named) is a loop, not a hand-off, so `isSelfDispatch` drops it. The entry is a self-contained card in `isSelfContainedCard`, so streamed output after it starts a new entry instead of being glued onto the pill. CLI tests that assert a message payload must call `isolateAgentEnv([CALLER_AGENT_ID_ENV_VAR, CALLER_TAB_ID_ENV_VAR])`, or they fail when run from inside an agent shell.
- **Ordering the Auto Run run list from the picker:** `applySelectionOrder(documents, selectedFilenames, createEntry)`, `selectFolderFiles(prev, files)`, `deselectFolderFiles()`, `selectAllDocuments()` in `src/renderer/utils/documentSelectionOrder.ts`. The run list is an ordered program - document 1 runs, then document 2 - and the "Select Documents" picker is where that order is authored, so selection order IS run order. The picker used to emit `[...documentsAlreadyInTheList, ...newlySelected]`, which pinned anything already added to the front: a user who reopened the picker and clicked folders in the order they wanted them to run got the old order back with the new folders bolted on the end. `applySelectionOrder` rebuilds the list from the selection alone, reusing existing entries so ids, reset flags, and duplicate rows survive and every duplicate stays grouped with its original. `selectFolderFiles` deletes before re-adding so a folder's documents land as one contiguous block at the end even when one of them was already picked individually - without that, clicking a folder leaves a stray document behind at an earlier position. Do NOT rebuild the list from `allDocuments` or the document tree: both are alphabetical, and the user's click order is the only place the intended run order exists.

- **Whether an Auto Run is parked waiting on the user:** `useAutoRunErrorPaused(sessionId)` in `src/renderer/hooks/batch/useAutoRunPause.ts`. `batchRunState.isRunning` stays true through a pause, so a surface that asks "is a run active?" to decide whether to lock the document locks it during the exact pause that exists to let the user edit: an agent error the user has to fix, or a `MAESTRO:HITL` gate answered by ticking the box the marker sits above. Split the two questions - `isRunning` means the run is alive (so Stop stays offered), `errorPaused` means it is idle and asking (so the editor and the preview checkboxes open back up). Read the flag through this hook, NEVER off the `batchRunState` prop: the chain store -> `useBatchProcessor` -> `useBatchHandlers` -> `App` -> `RightPanel` -> `AutoRun` drops `errorPaused` updates through `updateBatchStateAndBroadcast`/`UPDATE_PROGRESS`, so a prop read reports `false` for a run that is plainly paused on screen. (The legacy `src/web/mobile` surface this rule was also written for read `autoRunState.errorPaused` straight off the wire; that tree is retired, and the browser now runs the same renderer through the web-desktop bundle, so it goes through the hook like every other surface.)

- **Tap-vs-hold on a microphone button:** `usePressAndHold({ holdThresholdMs, onHoldStart, onHoldEnd, onTap })` in `src/renderer/hooks/utils/usePressAndHold.ts`. A microphone button has to answer two different habits and a voice UI that picks one has half its users fighting it: someone dictating a paragraph holds the button like a walkie-talkie, and someone having a conversation taps it once and forgets about it. Both surfaces that offer that button - the voice HUD's talk control and the document chat's push button - classify against the SAME `resolveHoldThresholdMs(...)` the global hotkey uses (`src/shared/acappella/voice-controls.ts`), so a button and a key can never decide "hold" at different moments. Three behaviours are the reason it is a hook rather than two copies of a `setTimeout`, and each one is a bug a copy would have: the release listener is on the WINDOW, because an element-scoped `onPointerUp` never fires when the user drags off the button - the commonest way to abort a press - and the floor is then left open with nothing holding it; UNMOUNT releases the hold, since a press interrupted by the surface closing otherwise leaves a hot microphone with no widget attached to it; and the press state lives in refs, because the window listener is attached once and would otherwise read a stale `holding` from the render it was created in. The callbacks are read through a ref for the same reason, so a caller passing inline arrows cannot tear the listener down mid-press. Do NOT hand-roll another hold timer beside a microphone.
- **Chatting with a document:** `services/documentChat.ts` (the conversation) plus `hooks/ui/useDocumentChat.ts` (live state) and `components/DocumentChat/` (the bubble). The chat is an ORDINARY AI TAB tagged with `AITab.documentOrigin`, not a second chat system, and everything the feature promises falls out of that one decision: it persists across restarts because sessions are already written to disk; popping out is `focusAiTabInSession`; and a spoken turn lands in the same conversation because `RosterTab.documentPath` carries the binding to the voice router (`documentTabId` in `voice-session-service.ts` prefers it over the per-session `lastDispatch`, which is the only source that survives a relaunch). The tab is created HIDDEN, exactly like a cross-agent consult tab and for the same reason - chatting about a file from a preview pane is not the user asking for a chip in the strip - which is why `buildRoutingTabs` carves document chats out of its hidden-tab filter: dropping them made a spoken turn open a SECOND tab about a file the user had already been typing to. Three rules that are easy to get wrong: the opening prompt goes through the shared `buildDocumentOpeningPrompt(scope, request, modality)`, and `'typed'` exists so a chat panel never tells the agent it is a spoken conversation; `readDocumentChatView` draws QUEUED messages as pending bubbles, because a message behind a working agent is not in the transcript yet and a chat that swallows what you typed reads as broken; and RESET reveals the old tab rather than deleting it, so the button can never cost the user a transcript.
