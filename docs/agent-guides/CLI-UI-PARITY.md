# CLI / UI Parity Audit

Rule (constitutional, see CLAUDE.md): anything a person can do by pointing and
clicking in Maestro, an agent MUST be able to do through `maestro-cli`, through
the same code path. A UI action ships with its CLI verb. This file records where
that holds today, where it does not yet, and why.

Audited 2026-08-19 against the three surfaces that define "clickable": the
keyboard shortcut registry (`src/renderer/constants/shortcuts.ts`), the Quick
Actions command builders (`src/renderer/components/QuickActionsModal/commands/`),
and the Left Bar context menus (`src/renderer/components/SessionList/`). The
authoritative CLI surface is `docs/cli-reference.md`, generated from the
Commander tree by `npm run gen:cli-reference`.

## Focus belongs to the human (`--background` / `--focus`)

Provider translation (`update-agent --provider`) uses `provider_translation`, which forwards to the same migration callback as Edit Agent. Its dedicated transport prevents a newer CLI's preflight/apply from falling through to an older desktop's destructive provider settings patch. `--migration-plan` targets a reviewed operation; `--dry-run --json` supplies its ID for a Cue shell Command node. This operation changes the active provider; it is not an independent replica sync API.

An agent may create a surface. It may not decide the human should be looking at
it. Every verb that can move the Maestro view or raise a notice carries a
`background` bit so a caller that wants to stay out of the way has a way to say
so, and the bundled system prompt tells agents to pass it by DEFAULT.

`background: true` means exactly two things, everywhere: the active **agent**
does not change, and the active **tab** inside any agent does not change. The
surface is still created and still addressable - it lands in the tab bar the way
a browser opens a background tab. "Created but invisible" is a different bug and
must never pass as background placement.

### The flag is ADDITIVE. One verb's default changed.

The defect was that an agent which wanted to be polite had no way to ask. It was
**not** that the verbs focus. Every verb behaves exactly as it did before when
the flag is absent, so no existing script, playbook, Cue prompt, or
muscle-memory invocation changes - what changed is the guidance, which now says
to pass the flag rather than leaving each agent to guess.

That split matters: flipping the CLI defaults would silently rewrite behaviour
for every caller that has already shipped, including the web and mobile clients,
which send the same messages and legitimately DO want to focus. Flipping the
guidance changes only what new calls ask for.

The one exception is `refresh-auto-run`, whose CLI default is now background.
Its focusing default only switched agents when the target was NOT on screen, so
it fired exactly when the user was looking elsewhere: every Cue script or agent
turn that ended with an unflagged refresh yanked the user to that agent. The
flip is CLI-side (`CLI_BACKGROUND_DEFAULTS`), so a web client that omits the
field still gets the old behaviour, and `--focus` restores it from the CLI.

`focus-agent`, `send --tab`, `open` and `open-graph` exist TO move the view - the
caller named that intent, and the graph is a full-window overlay whose only
effect IS being looked at, so a background one would do nothing. They are
deliberately absent from the table and must stay that way.

`--focus` ships on every verb even where it currently just names the default,
because a future default flip needs the escape hatch to already exist.

`browser-pick --queue` is quiet by itself: it sends the pick as its own queued
message and never touches the view, so `--background` and `--focus` have nothing
left to decide there.

### Two verbs of one command name: `dispatch`

`dispatch --new-tab` is background by default and `dispatch` (writing to an
existing tab) is not. Both are correct - one creates a surface the caller will
address by id, the other writes into a conversation - and they are why the table
is keyed by **verb** rather than by message. `send_command` is also what
`create-worktree` uses to deliver its optional `--message`, and that call carries
the placement the CALLER resolved for `create-worktree` rather than re-resolving
as `dispatch`. Without that, `create-worktree --background --message "..."`
created the agent quietly and was then yanked onto it one message later, which
reads as the flag not working.

### `ask` is not `dispatch --background`

`--background` decides where the VIEW lands. It does not decide which
conversation the prompt joins. A backgrounded `dispatch` still writes into the
target's active tab, so a question sent that way lands in the middle of whatever
the user has open with that agent - quietly, which is worse, because they find it
later with no idea where it came from.

`maestro-cli ask` is the verb for a question. It routes to the cross-agent
consult path (`cross_agent_ask` -> `consultAgent` -> `runCrossAgentAsk` ->
`sendCrossAgentRequest`), the same one a typed `@mention` takes: a hidden tab on
the target, a fresh context, no focus, no unread, and the answer returned to the
caller. It carries no `--background` flag because there is no foreground form of
it - a consult that took over the screen would not be a consult.

Against a headless host (`maestro-cli host`) there is no renderer to hand the
consult to, so `cross_agent_ask` is answered by the library's consult service
(`createRuntimeConsults()` in `src/shared/maestro-lib/runtime/consults.ts`): the
same hidden consult tab per asking agent, the same read-only rule, the answer
returned to the caller, and `maestro-cli group-chat` runs a whole round the same
way (`createRuntimeGroupChats()`). A desktop keeps the renderer hop until the
desktop hosts on the runtime.

The rule for a new agent-to-agent verb: if the caller wants an ANSWER, it rides
the consult path; if it wants the other agent to DO something, it rides dispatch
and the placement flags apply.

### Verbs that accept the flag and ignore it

`refresh-files` renders no notice and moves no selection: the Files panel it
refreshes is only drawn for the agent already on screen. `live on` / `live off`
move no view either: every window's LIVE pill follows the switch. They still
accept `--background`, and `ALREADY_QUIET_VERBS` in `shared/focusPlacement.ts`
is where that is recorded.

This is not a placeholder. The guidance agents are given is "pass `--background`
unless the user asked to be taken there", and commander **rejects an unknown
option** - so one verb that refused the flag would turn a polite habit into a
failed command, and the rule would have to be taught as a lookup table instead of
a sentence. A verb belongs on that list only while it is genuinely quiet; the
moment one grows a notice or a selection change it moves into
`CLI_BACKGROUND_DEFAULTS` and the flag starts meaning something, with no change
to anything already calling it.

### Placement is not error suppression

A failed command still raises its toast with `background: true` set. The flag
says where a surface goes, not whether the user gets to hear that something
broke - `openTerminalTab`'s "Failed to start terminal" and `configureAutoRun`'s
"Worktree Error" toasts are deliberately ungated.

### The contract lives in one module

`src/shared/focusPlacement.ts`, imported by both ends:

- CLI: `resolveBackgroundFlag(flags, verb)` turns `--background` / `--focus`
  into the bit that goes on the wire. Keyed by **verb, not message**: `tab new
--prompt` and `dispatch --new-tab` both send `new_ai_tab_with_prompt` and
  disagree about the default, so keying by message would force one of them to
  change behaviour.
- Main process: `readBackgroundField(message)` reads it back, and it is an
  **opt-in** - only a literal `true` counts.

> [!WARNING]
> Never write `message.background !== false` in a handler. That reads an absent
> field as an opt-in and silently stops the verb from focusing, which breaks
> every existing caller at once. It is the single most likely way this change
> regresses, and it is why the read goes through one shared function.

### `--no-switch` is NOT a spelling of `--background`

They coexist on `open-file` and mean different things:

- `--no-switch` stays on the current agent and **still activates the tab there**.
  If you were already on that agent, your view still changes.
- `--background` changes nothing currently rendered, on any agent.

Passing both is fine; `--background` is strictly stronger and wins. Folding the
first into the second would silently change behaviour for everyone already
passing it. Worth knowing regardless: `--no-switch` reads like it means
`--background` and does not, so anyone who reached for it probably wanted the
stronger one.

### Renderer side

Background placement is the absence of a focus patch: the four `*FocusFields`
helpers in `src/renderer/utils/tabHelpers/focusFields.ts` are what make a tab visible, so
`createTab({ activate: false })`, `addTerminalTab(s, tab, { activate: false })`
and `handleOpenFileTab(file, { activate: false })` simply do not spread one.
`open_file_tab` is the one three-state path, because it has to serve both flags:

```
neither       -> switch agent, activate tab   (default)
--no-switch   -> stay on agent, activate tab
--background  -> touch nothing rendered anywhere
```

### Verifying

Use `Claude/Tools/focus_watch.py`, never your eyes: it logs every focus
transition, so an inert flag cannot pass as a fix. **Two runs per verb:**

1. **With `--background`**, against a _different_ agent than the focused one:
   the log stays empty, and the surface still exists (`tab show`,
   `session list`, `list terminals`).
2. **Without the flag**: the log records exactly the jump it recorded before.
   Since no default changed (except `refresh-auto-run`), an unflagged call
   that stops focusing is a regression - and it is the failure mode this design is most likely to
   produce.

## How to add a scriptable write

Persistent per-agent and per-tab state goes through **one** message:
`update_session_config`. It is the only write path that has all three of the
things a scriptable operation needs:

1. An **allowlist** in the renderer, so the CLI cannot write arbitrary `Session`
   internals.
2. A **response channel**, so the CLI learns whether the write landed instead of
   assuming it did.
3. A **`setMany` flush** before the ack, so a read taken immediately after the
   write sees the new value rather than racing the renderer's 2 second debounced
   persistence.

The handler lives in `useAppRemoteEventListeners.ts`
(`maestro:remoteUpdateSessionConfig`). It holds two allowlists: agent fields,
and - when the patch carries a `tabId` - AI tab fields. Adding a scriptable
field usually means one allowlist entry plus one CLI verb.

Do **not** reach for the older `mainWindow.webContents.send('remote:...')`
pattern (`star_tab`, `toggle_bookmark`, `reorder_tab`) for new state. Those are
fire-and-forget: they report success as soon as the message is handed to the
renderer, they do not confirm the renderer applied anything, and they do not
flush. They stay because the mobile web client speaks them.

Prefer **explicit set operations over toggles**. A toggle is unusable from a
script: re-running it flips back, and an agent driving the desktop has no
reliable way to observe the result mid-flight. `bookmark`/`unbookmark`,
`tab star`/`tab unstar`, and `tab read`/`tab unread` are all set verbs for this
reason.

Every write should have a matching read. A verb an agent cannot verify is a verb
an agent has to guess about.

A tab-targeted verb takes its tab id through `resolveTabEntry()`
(`src/cli/services/session-command.ts`), which accepts an exact id, a unique
prefix, or the literal `active` - the tab that agent has selected, with
`-a <agent-id>` naming whose. Use the helper rather than matching ids yourself:
it returns the whole `DesktopTabEntry`, so a verb that needs the current value
(`tab thinking cycle`) reads it from the same call that resolved the tab instead
of taking a second round trip or trusting a value the caller guessed.

## When the desktop app is absent

A verb that reaches the desktop through the bridge cannot run without it, and an
agent calling it has to be able to tell "the app is down" from "the command was
rejected". Every app-dependent verb therefore reports a missing app as ONE
outcome: message `Maestro desktop app is not running or not reachable`, JSON code
`MAESTRO_NOT_RUNNING`, exit 3, in human and `--json` output alike.

- **Writing a new verb:** put `exitIfMaestroNotRunning(error, { json })`
  (`src/cli/services/session-command.ts`) first in the catch that wraps its
  bridge call.
- **Never classify the error by its wording.** `MaestroClient.connect()` throws
  a typed `MaestroNotRunningError`, and catches that flattened it to a string are
  how a dozen verbs used to exit 1 under five different messages.
- **The table-driven `src/__tests__/cli/app-not-running.test.ts` covers every
  existing verb.** Add a row for a new one.

A verb that does NOT need the app is one an agent can run on a headless server.
Which verbs those are, how the CLI picks its data directory there, and what
a headless run records is in [CLI-HEADLESS.md](CLI-HEADLESS.md). No UI action
changed with this: no row in Covered or Open gaps moved.

## Covered

Notification center history uses the live desktop `notificationStore` over a request-response bridge. Main owns durable append/read/clear mutations in `maestro-notification-history.json`; renderer snapshots are synchronized across windows, and CLI results await committed writes. `notify inbox list --unread` filters the snapshot, `read <id>` / `read-all` update read state, `clear` clears history, `dismiss [id]` dismisses one entry or clears visible toasts, and `activate <id>` / `link <id>` run the same entry and inline-link actions as the UI. Every result includes the resulting unread count and history. `detail <id>` / `collapse` expand and collapse the same in-inbox details view. The five opt-in inbox preferences are registered settings and can be changed with `settings set <key> <value>`. `open notification-center` and `notify inbox open` open the app-level popover even when the Left Bar is hidden. The inbox is switched on by the `notificationCenterEnabled` setting (`settings set notificationCenterEnabled true`); while it is off, every `notify inbox` verb except `dismiss` with no id fails with the enable hint, and `open notification-center` refuses.

`maestro-cli lite` addresses a **running Lite client**, not the full host's CLI
server (the third case in [CLI-HEADLESS.md](CLI-HEADLESS.md#need-a-running-lite-client):
it needs neither the desktop app nor a data directory, and without a client every
subcommand exits 1 with `success: false`). It calls the same native dispatcher used by Lite's trusted connection UI
and menu. Profile persistence, URL/SSH validation, TLS, host authentication,
validated identity, and tunnel ownership remain native; the CLI implements none
of those policies. The endpoint imports no full-mode process manager, stores,
agent detector, or web server.

Discovery lives in `lite-control.json` inside Lite's isolated user-data directory.
The transport is a per-boot authenticated Windows named pipe or Unix socket,
not a network listener: remote host web content cannot access it. The desktop
writes it under `app.getPath('userData')/Lite`; the CLI finds the same directory
through `resolveUserDataDir()` plus `Lite`, or `$MAESTRO_USER_DATA/Lite` when a
base-path override is supplied. A dev checkout's desktop writes under its own
`maestro` or `maestro-dev` directory, which a CLI started from a terminal cannot
guess, so pass `--user-data` there. To select an isolated instance
explicitly, launch `Maestro --lite --lite-user-data <directory>` and run
`maestro-cli lite --user-data <directory> ...`. These flags name the **final**
Lite directory, without appending another `Lite`. Relative CLI paths and `~`
use the existing CLI path resolver.

Startup checks ownership by probing the discovered OS-local endpoint, not by
trusting a PID that may have been reused. Missing/refused endpoints permit stale
discovery recovery; accepting endpoints retain ownership regardless of recorded
PID. Only Lite's generated local named-pipe/temporary Unix socket shapes are
eligible for a probe; incomplete or nonlocal discovery is replaced without
connecting to it. Permission errors and inconclusive probe timeouts fail closed.
Native Lite also holds its isolated user-data single-instance lock during startup.

All commands return readable JSON, including current native state after writes;
`profile read` and `profile save` also return the individual `profile`. State
includes connection `status`, optional `error`/`selected`, `picker`,
`commandsVisible`, `profiles`, and SSH config `aliases`. Profiles expose connection URLs (including Remote
Control path tokens) to the authorized local caller; never publish this output
or the local discovery secret. Save takes a complete JSON file with the same
fields as read: `id`, `name`, `transport` (`ssh` or `https`), `url`, and `ssh`
for SSH. A minimal direct profile is:

```json
{
	"id": "my-host",
	"name": "My host",
	"transport": "https",
	"url": "https://host.example/remote-control-token"
}
```

Deletion, validated-identity reset, and close require `--yes`, never native
dialogs. Dismiss returns to the remote view, or stays on setup when disconnected;
it never closes Lite. Save and connect uses `lite profile save` followed by
`lite connect <id>` only after a successful save. A connection's asynchronous progress is readable through `lite
status`; connection success never bypasses host-side login or identity checks.
Closing/disconnecting Lite never stops host workloads. Errors return
`success: false` with a nonzero exit status. A missing acknowledgement reports
uncertainty and never retries a potentially mutating command; read status before
acting again.

## Pianola owner scope configuration

`pianola supervise scope --request-owner-approval` requests one native host
confirmation of the exact selection, future-agent policy and manager, with the
previous registry shown for review. The host uses the same `configurePianolaScope`
service and migration lock as the native and bound web owner UI. CLI credentials,
payload principals and manager IDs never establish owner identity. Desktop owner
restrictions still apply; a restricted desktop cannot replace a configured web owner.

Exact standing selections reconcile without a dialog, including when the flag is
present. New or changed selections require the explicit flag and a positive native
dialog answer within 60 seconds. The host checks the original registry, rules,
identity, enabled feature, window and authenticated caller again inside the shared
lock, including the existing enrollment revision to reject changed and restored scopes.
Cancellation, timeout, revocation, changed configuration or an unknown native
census cannot publish the operation. JSON returns the committed target and migration
result, or `NeedsConfiguration`, `Denied` or `Unknown`; failures exit nonzero.

## Open gaps

Ranked by how often an agent is likely to hit them. Every entry is buildable
work; UI actions left without a verb on purpose are listed under
[Not mirrored by design](#not-mirrored-by-design).

1. **Merge Into a new merged agent.** The Merge Into modal's "create new
   session" option builds a fresh agent from both transcripts. `tab merge`
   only merges into an existing tab; the new-agent path reports its result
   through `onSessionCreated`, which would need the new agent's id threaded
   back to `runRemoteTabContextOp()`.
2. **Pipeline Graph view selection** (the selector's pipeline / agent / All
   Pipelines choice, and the dashboard's "View in Graph"). `open cue --tab
pipeline` reaches the graph but cannot name what it shows. Pure view state
   on a read-only canvas, with nothing for an agent to read back; the data it
   filters is already readable through `cue pipeline` and `cue list`. Closing
   it means carrying a target through `open_modal` into `CueModal`'s
   `pendingGraphTarget`.
3. **`cue pipeline` beside a headless host.** The six `cue pipeline` verbs
   manage `cue-pipeline-layout.json`, the desktop Pipeline Graph's own document
   (node positions and colors the engine never reads), through desktop
   callbacks a `maestro-cli host` does not have. Beside a host each verb exits
   1 with `CUE_PIPELINE_HEADLESS_MESSAGE` (`src/cli/commands/cue-pipeline.ts`),
   which points at cue.yaml (`cue schedule`, `cue model`) instead. Closing it
   means moving the layout mutations (`pipeline-layout-mutations.ts`) behind a
   service the host also serves, and deciding how a layout edited with no
   window reconciles with an open editor.
4. **File editor selection and find-bar actions** (right-click a selection
   in the File Preview editor: Quote in Message, Send to Agent, Copy; the find
   bar's Replace / Replace All). Each acts on a live text selection or match in
   the user's editor, which the CLI has no handle on. The capabilities are
   reachable without it: an agent reads the file, quotes `path:lines` itself,
   and hands the text over with `dispatch` / `send`; replacing text is an edit
   to the file on disk, which an agent makes directly and `open-file` shows.
5. **The SQLite viewer's "Enable editing" unlock** (File Preview on a
   database: the summary strip's per-tab switch, off by default). The tab's
   grant is a token only that tab holds (`enableSqliteEditing()` in
   `src/main/sqlite/sqlite-editing.ts`), so a CLI call never inherits or flips
   a tab's unlock: the click is the person's consent for that tab. The CLI
   mirror is the per-call `--enable-editing` flag on each `maestro-cli sqlite`
   WRITE verb (`sqlite set`, the cell edit; `sqlite insert` and
   `sqlite delete`, the row insert and delete; `sqlite undo`, the
   strip's Undo; `sqlite query`, Query mode's statements once the unlock
   lifts the read-only assertion, and its Dry run with `--dry-run`;
   `sqlite transaction`, Query mode's Begin transaction through Commit or
   Roll back, in one call since the transaction cannot outlive it), which enables
   editing for that one call and disables it after through the same two
   functions, and writes through `beginSqliteWrite()` (or, for a statement,
   `beginSqliteWorkerWrite()`; for a dry run, `beginSqliteWorkerTrial()`,
   which takes no backup because it always rolls back) like the tab, so a CLI
   write also takes the once-per-session backup before the file's first change. The switch itself has no verb: it holds no state a later CLI call
   could use.
6. **Verify whether a provider CLI is detected after installing it.**
   `install-command <provider>` prints the install command so an agent can run
   it in its own shell, and the desktop refreshes detection on Retry via
   `agents:reprobe`, but there is no `maestro-cli` read verb yet that queries
   `agents:detect` or `agents:reprobe` to report detected provider binaries.
   Agents can check `command -v <binary>` (or `where <binary>` on Windows) in
   their own shell.
7. **An `@mention` in a message `maestro-cli` sends straight to a host.** A
   hosted agent's own `@mention` runs when it is typed in its composer, waits
   in its queue, or arrives in a `maestro-cli dispatch`: a dispatch to a hosted
   agent of this desktop now goes through the running desktop (#2148), which
   plans the mention against its roster, consults, and sends the host only the
   turn, with `agentContext` / `agentNotes` (#2140). `--routing` and
   `--notify-on-complete` work on that path, and the callback settles when the
   host's turn ends (`feedHostedTurnToDispatchCallbacks()`). Both host kinds
   now place the two fields in the prompt, and a host too old to know them
   gets the text inside the message (#2148). Still open: `maestro-cli send` to
   a hosted agent, a `dispatch` with no desktop running, and a verb aimed at
   `peer:agent` reach the host directly (`liftedPeerTarget()`,
   `runPeerDispatch()`). There `dispatch` refuses `--routing` and
   `--notify-on-complete` with the reason, and a headless host consults nobody
   for a mention in the text. Closing it means planning the mention in the CLI
   or on the host.
8. **What a headless host (`maestro-cli host`) still refuses.** An audit of
   every refusal (#2140) found none left that a person reaches from a hosted
   agent's desktop UI, because the desktop does each one itself: it runs
   `!command` over SSH (`runShellCommand()`), saves the playbook, creates the
   Auto Run worktree as an SSH worktree agent, always sends `launch: true`,
   switches or converts a provider locally and syncs only `toolType`, and
   opens `/wizard` in a host tab. The host keeps these refusals for a verb sent
   straight to it (`peer:agent`), each with the reason: a terminal command,
   `dispatch --notify-on-complete`, `dispatch --routing`, `auto-run --save-as`,
   `auto-run --worktree`, an Auto Run configuration without `--launch`, a
   provider change that needs translation, and `/wizard` sent as text. An
   older host also still refuses `/btw` and a steer. Closing one means doing
   on the host what the desktop does for it today.
9. **Steer for a hosted Claude agent whose host has no maestro-p.** Move to
   Host copies only the CLI bundle (`remote-install.ts`). Without the maestro-p
   installer's copy on the host, the agent runs over `--print` there, and
   `queue steer` answers `not-steerable` with the reason. Closing it means
   installing maestro-p (with node-pty) during Move to Host.
10. **A headless host's waiting messages after a restart.** The host's queue is
    in memory, so restarting `maestro-cli host` loses held and waiting
    messages, where the desktop persists `executionQueue`. Closing it needs a
    write of each agent's waiting items through the repository, and a
    Federation decision for the field.

## Not mirrored by design

These are UI actions deliberately left without a CLI verb. Each entry states
why: the action is interactive by nature, sits behind a human-consent boundary,
or is a pure view preference with nothing for an agent to read back. A new
entry needs a stated reason, the same way a Covered row needs a verb.

- **The SQLite viewer's SQL editor and its completion** (File Preview on a
  database: the Browse / Query switch, typing SQL with table and column names
  completed from the open database). Typing into an editor has no result to
  read back, and the switch is a remembered view preference. The names the
  completion offers are readable without it: `sqlite tables <path>` lists the
  objects and `sqlite schema <path> <object>` their columns, both through the
  same read-only open the completion catalog (`readSqliteColumnCatalog()`)
  uses. Running a statement has a result, and is mirrored by `sqlite query`
  (see Covered).
- **Grooming on Merge Into and Send to Agent** (the modals' "clean up the
  context" checkbox). `tab merge` and `tab transfer` always move the
  transcript verbatim: context carried to another agent or provider is never
  summarized or trimmed. Only `tab compact` summarizes, because that is what
  Compact is.
- **Git actions** (View Git Log / Diff, Pull, Push, Change Branch, Create PR).
  Deliberately not mirrored: these open modals over `useGitAgentActions`, and an
  agent already has `git` and `gh` in its shell, which is strictly more capable.
  Only the modal-opening is unavailable, not the capability.
- **Wizard and interactive pickers** (New Agent Wizard, Fuzzy File Search,
  Tab Switcher, Search: Messages). These are interactive by definition; the
  underlying data is reachable through `list`, `session show`, and
  `director-notes history`.
- **Expand a diagram or image to the pan/zoom viewer.** The viewer opens on
  an element already rendered in a transcript or document
  (`openZoomViewer(element)`), and a transcript element has no address the
  CLI can name. The capability is still reachable: `open-file <image>` opens
  the file preview's `ImageViewer`, which shares the same `usePanZoom`, and
  an agent can write a diagram to a `.mmd` file and `open-file` it. Pure
  viewing; there is no result for an agent to read back.
- **Drag-resized pane sizes and phone composer folds kept in renderer
  localStorage** (the Auto Run document dropdown's height via
  `useResizableDropdownHeight`, the Document Graph preview width via
  `usePersistedPanelWidth`, and the phone composer fold in `InputArea` and
  `GroupChatInput` via `usePersistedToggle` under `phone.composer.collapsed` and
  `phone.groupChatComposer.collapsed`). Pure per-device view preferences with
  nothing for an agent to act on; the values never reach main, so a verb needs
  a renderer round trip. Double-click on the grip resets pane sizes; a tap or
  swipe on `PhoneComposerHandle` toggles the fold.
- **Quit When Idle** (the `QuitConfirmModal` checkbox when the user quits while
  operations are running, and the read-only `QuitWhenIdleIndicator` pill with
  its Cancel button above the AI and Group Chat composers). Armed from the
  native desktop quit-confirmation flow (`useQuitWhenIdle` polls
  `collectActiveOperations`, including busy group chats, and calls
  `confirmQuit` once everything goes idle); a CLI agent never quits the host
  desktop app.
- **Turn browser Design Mode on or off** (address-bar pointer button,
  Cmd+Shift+C, palette "Design Mode: Pick an Element"). The mode only arms
  a hover overlay for a person's pointer; there is nothing for a script to
  point with once it is on. The outcome it leads to, an element or a region
  added to the message, is covered by `browser-pick <tab> --selector <css>`
  or `browser-pick <tab> --rect <x,y,w,h>`, which run the same capture,
  crop, and delivery code as a click or a drag, without the overlay
  (`--queue` sends it as its own queued message, as the card's Queue button
  does).
  The mode is sticky per browser tab (`BrowserTab.designMode`, saved with
  the tab): it survives page loads, tab switches, Add to Message and
  restarts, and only Escape and the toggle turn it off. It is still a mode
  for a person's pointer, so the gap stays open on the same reasoning, and
  no read reports the flag either (`session list --type browser` lists a
  browser tab's id, title, url and visibility, not its mode). Closing it
  means a `browser-design-mode <tab> [on|off] [--json]` verb that writes
  the flag through `updateBrowserTab()`, as the toggle does, and reads it
  back.
  Holding Space to use the page and clicking a crumb in the hover label
  need no verb: both are pointer gestures with no effect of their own, an
  agent drives the page through Coworking (`browser_click`, `browser_type`),
  and `browser-pick --selector` picks any ancestor directly. Dragging the
  box is `--rect` (guest CSS px, the box a drag would draw).
- **Log in to a provider account** (Usage Dashboard quota row "Log in",
  palette "Reauthenticate Provider"). The login is an interactive OAuth or
  device-code flow in a PTY, so there is nothing a non-interactive verb could
  complete. The capability is reachable from an agent's shell as
  `CODEX_HOME=<dir> codex login` / `CLAUDE_CONFIG_DIR=<dir> claude` then
  `/login`. Verify the login afterwards with `stats-plan-usage` (it reads the
  cached snapshot; the tab's Refresh re-sample has no verb yet).
- **Pianola learned suggestion review** (accept, edit, or reject). When owner
  identity settings are absent or empty, a verified local native desktop sender
  is the owner by default. Configured web identity is opt-in; explicit or
  malformed restrictions still apply. Each review requires explicit human
  consent in the native window or through an authorized configured web identity.
  CLI and agent calls cannot supply that consent or impersonate the human.
  Existing serialized identity keys and principal values remain supported;
  these UI actions do not migrate or reinterpret prior evidence.
- **Host LAN and Tailscale access controls** (enable, disable, select a LAN
  interface, and inspect access state in Connect another device / Manage access).
  These remain in the protected native host window as a deliberate human-consent
  design choice. Enabling a private listener requires the host owner's review;
  no CLI verbs expose these controls. This is not Live mode: the LIVE pill
  has no consent step, so `live on|off` mirrors it (see the Covered row).
- **Run a DataviewJS block again, or Run once** (Run again on a block whose
  script timed out, crashed its sandbox, or failed to load; Run once on the
  trust prompt of a block in a vault that is not trusted, and Run on an
  inline `$=` span there). The CLI can trust
  the vault (`dataview trust <root>`), which is what Run once avoids, but it
  cannot run one block. Deliberate: DataviewJS renders
  in the desktop app only (spec D8), so the CLI never runs note scripts, and
  `dataview query` on a `dataviewjs` block exits 2. The block's source is
  readable with `dataview query <file> --json`; there is no rendered output
  for an agent to read back.
- **Upload local files to the host from a composer** (the Upload button on
  the AI composer and, since step 5 of the composer parity plan, the Group
  Chat composer). Web-desktop only: it copies files from the BROWSER's device
  to the host and appends their `@path` mentions to the draft. There is no
  CLI verb, and none is planned: an agent runs on the host, so the files it
  would upload are already there, and it can mention them in `dispatch` or
  `group-chat` text directly.
- **Attach images to a Group Chat room** (the Attach button, paste, and drag-and-drop
  in the Group Chat composer). The room gates image attach on whether its
  moderator's provider supports image input (`supportsImageInput`). The CLI's
  `group-chat send` verb accepts text only (`<message>` or `--message-file`) and
  has no image attachment flag, so the moderator capability gate is not needed
  on the CLI send path.
- **Reorder a staged image, or drag one into a Group Chat room draft.** The
  room's strip renumbers `Screenshot N` when a thumbnail moves, and a drag
  inserts that reference once. `group-chat send` takes the final text, so an
  agent can write `Screenshot N` directly; the CLI stages no images and has no
  strip to reorder. The action exists to keep the desktop thumbnails and the
  draft in sync, which is a view operation with nothing to read back.

### Backstage plugin updates

| UI action                                                     | CLI path                                       | Shared implementation / read-back                                                    |
| ------------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------ |
| Extensions: update an installed plugin from a local directory | `maestro-cli plugin update <directory> --json` | `plugins:update` → `PluginManager.update`; preserves data and rechecks authorization |
| Inspect installed plugin state                                | `maestro-cli plugin list --json`               | `plugins:list`; versions, enabled state, signature and load status                   |

Plugin-defined settings inside isolated panels have no universal CLI schema. Those
remain plugin-specific API operations; host consent cannot be auto-approved from a
CLI call and still requires the protected consent window.
