# Claude Code and Codex native mapping

Status (2026-10-17): **Claude Code 2.1.296 -> Codex 0.162.1** and **Codex 0.162.1 -> Claude Code 2.1.296** remain **unverified**. These are the minimum versions and sole declared synthetic schema-coverage versions; no direction is native-certified for any version. Native acceptance was explicitly skipped on 2026-10-17; certification is deferred and no native evidence date exists. Schema inspection, structural readback and lint are not native resume evidence. See [[provider-translation-layer]] for the acceptance record and later static checks.

`translation/support.ts` declares `minVersion` and `testedVersions` and shares `translationVersionLimitation()` across registry, adapters and acceptance-driver preflight. Unparseable or below-minimum versions block with `unknown-version`. Valid semver versions at or above the minimum outside the tested list warn with `untested-version`, naming the installed and tested versions. A direction certified for tested versions remains unverified on any untested version. Per-record schema checks still block malformed records, invalid content and other extraction failures.

## Transport and projection

`parseNativeLines` is shared by the native History readers and translation. History's flattened `SessionMessage.content` is never an import transport. `PortableRecord.native` retains each parsed row; a separate SHA-256 artifact retains the entire original file including malformed/unknown rows, whitespace and line endings.

Extraction is native-format specific. The shared reconciler keys original provider/account/session/event identity and records generated native lineage. A return hop reads new native rows, unions new original records and reprojects a fresh session. It never appends text copied from Maestro's visible transcript. Previously parked destination sessions with new divergent work block rather than silently merge branches.

### Active compaction window

The destination receives the source provider's own latest compaction summary plus later conversational records. For Claude, the window starts at the first `isCompactSummary: true` user row after the last `compact_boundary`, even when attachment rows intervene. For Codex, it starts with the last `compacted` row's non-empty `payload.replacement_history`, mapped through the ordinary Responses-item mapper, or its legacy `payload.message` as a user summary when replacement history is absent or empty, followed by later `response_item` rows. Maestro never writes a summary itself, truncates the source, or fabricates foreign compaction state. A latest boundary with no usable summary/history blocks with `missing-compaction-history`.

Earlier records remain in portable data with `window: 'archived'`, and the archive retains the original transcript bytes. `activeContextRecords()` drives both native projections, context-capacity estimation and plan counts. Transcripts without a boundary keep all records active; legacy checkpoint records without a window flag also remain active. Claude projection builds a new parent chain from a root; Codex injects only active items. Edit Agent and CLI report active records carried and records archived before the last compaction. `compaction-window` is info, requiring no acceptance; `native-boundary` remains a warning for actual branches and sidechains.

Tool-link validation runs only over the active window, so an unanswered call before compaction does not block it. Reconciliation retains archived origins in the full checkpoint and refreshes known records' window flags on return hops; `projectedOriginKeys()` covers emitted items only. An A to B to A hop therefore retains archive evidence without re-importing pre-compaction history. See [[provider-translation-layer]] for synthetic coverage and probe results; neither establishes native resume certification.

### Session origin and interrupted turns

Project ownership uses the first declared Claude `cwd` or Codex `session_meta.payload.cwd`, with paths resolved through the selected native filesystem and checked by the canonical `isPathAtOrUnderRoot()`. An origin equal to or inside `identity.projectRoot` passes; an outside origin blocks with `native-project-root-mismatch`. Later cwd changes, including Codex turn context and moves outside the project, add one `native-cwd-drift` info entry per conversation without changing the origin or the archived directory evidence.

For both providers, within the active window, an unanswered tool call followed by later user/assistant conversational content blocks with `unfinished-tool-call`. A trailing unanswered call is a stopped turn: keep its portable block with `interrupted: true` and all original native bytes, omit that call from the destination in `projectConversation`, and emit `interrupted-tool-call-dropped` as a warning listing the call IDs. Tool-only rows, partial parallel results and runtime metadata do not advance the conversation. Completed parallel calls and surrounding text remain projected. Never invent a result or replay the call. Live busy tabs still defer before extraction.

### Limitation tiers and outcome telemetry

`TranslationLimitation.severity` is `info | warning | block`. Info needs no acceptance; warnings require acceptance; blocks prevent translation and cannot be accepted. Only blocks drive blocked plan status. Reuse `limitationsNeedingAcceptance()` from `translation/index.ts` for every acceptance check. `opaque-runtime-state`, `native-attachment-state`, `historical-instructions` and `native-cwd-drift` are info; possible data or behavior loss, interrupted calls and unverified native resume remain warnings. Edit Agent shows info in collapsed Notes; CLI prints a separate `Notes:` heading.

Deferred acceptance stores and compares only complete warning entries with `canonicalJson`, including tab, artifact, severity and message. New or changed warnings require review; changed info does not. Info-only plans apply without acceptance, while legacy code/artifact-only acceptance requires renewed review if warnings remain.

After every plan is built, `src/main/provider-translation-service.ts` emits one `provider-translation-plan` info event through main-process Sentry `captureMessage()`. The extra payload contains exactly `sourceProvider`, `destinationProvider`, `sourceVersion`, `destinationVersion`, `status`, `verification` and `limitationCounts`. Counts are grouped by severity (`info`, `warning`, `block`) and then code. No messages, paths, tab/session/agent IDs or content are included. The event measures a plan outcome, not native resume or a completed migration. See [[provider-translation-layer]] for the extraction probe and evidence limits.

## SSH filesystem and import mapping (2026-10-17)

The same transaction uses `TranslationFs` from `translation/fs-port.ts` for native files. `localTranslationFs` keeps local behavior; main supplies `createSshTranslationFs()` over the canonical remote-fs primitives for SSH agents. `TranslationArchive.archiveFs` is deliberately local. A remote source never selects local filesystem behavior when SSH resolution fails.

| Operation                       | SSH mapping                                                                                                                                                                                                                                                                     |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Provider/account identity       | `resolveSshTranslationHost()` resolves the configured target, then probes the remote binary with custom path/args/env. It reads remote `HOME`, `CLAUDE_CONFIG_DIR` and `CODEX_HOME` and applies `resolveAgentAccountKey()`                                                      |
| Project and memory identity     | Resolve physical paths through the SSH port, query Git's common directory with `execGitReadOnly()`, and discover Claude memory through the same port. Native paths remain POSIX on Windows hosts                                                                                |
| Native staging and verification | Read source bytes, create destination files, collect/project resources, read back and roll back owned writes on the remote host. Base64 payloads travel on stdin; uncertain writes are not retried blindly                                                                      |
| Codex import                    | Spawn remote `codex app-server` through `wrapSpawnWithSsh()` with pinned destination `CODEX_HOME`. `openCodexTranslationConnection()` feeds stdio to the existing RPC client for start/inject/list; rollout readback uses the SSH port. Ordinary SSH turns stay on `codex exec` |
| Managed knowledge               | Write `<remote HOME>/.maestro/provider-knowledge/<agent-hash>/<operation-id>/` through the port. Bind the saved SSH config fingerprint and home; local or different-host launches reject it                                                                                     |
| Local durability                | Keep original-byte archives, checkpoints, journals, process locks and Maestro's native-session mappings local. Status can inspect local records offline; native recovery/rollback requires the same remote and valid ownership                                                  |

Remote prerequisites are supported provider binaries, POSIX `sh`, `base64 -d`, `realpath` or working `readlink -f`, Git and GNU/BSD filesystem tools. The identity probe names missing base64/path-resolution support and failed binary probes; later transport errors also stop the operation. See the [SSH translation contract](../PROVIDER-SUPPORT.md#ssh-translation-boundaries-and-prerequisites) for the detailed tool list and boundaries. There is no blanket `remote-translation` block and no local fallback.

**SSH live check skipped**, confirmed from `.maestro/scratch/ssh-acceptance.json` (`skip: true`) and the Hardening log in [[provider-translation-layer]]. Claude Code to Codex and Codex to Claude Code remain unverified over SSH; certification is deferred and SSH Ensemble choices must stay disabled. Fake-remote service and RPC cases cover the intended round-trip, recovery and rollback paths, but were only authored and statically checked under the no-tests instruction. | -------------------------- | ------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Managed memory             | Operation-owned `<knowledge-root>/<agent-hash>/<operation-id>/memory` and linked topics, outside the project       | Host-supplied root, no Electron dependency in the library; shared index binding for both providers. | Instructions               | Existing CLAUDE/AGENTS canonical body, relative alias when compatible                                              | Distinct bodies block. Do not inject the same instruction body again through the knowledge index                                                                                                                                              |
| Skills                     | Claude `.claude/skills`, Codex `.agents/skills`; retain scripts/resources and owner execute bit                    | Original frontmatter archived. Unsupported hooks/tool/fork/runtime metadata skips native installation of the whole skill; knowledge access is not equivalent skill execution                                                                  |
| Subagents                  | Claude Markdown/YAML frontmatter ↔ Codex `.codex/agents/*.toml`                                                    | Name/description/instructions projected with actual YAML/TOML parsers. Unsupported models/effort/memory/tool controls remain limitations; no permission broadening                                                                            |
| Selected user resources    | Explicit files/subtrees within approved memory, skills, agents or instruction roots                                | No whole-account import, generated global memory summaries or provider databases. Directory links archived without implicit traversal                                                                                                         |

Resource return hops use the common baseline, native/managed variants and deletion tombstones. Conflicts retain both bodies and block. Existing unrelated native files are not overwritten; rollback touches only tracked unchanged output. Launch binding and Memory Viewer are the discovery interfaces, not a second editor or an account-global memory import.

The Instructions, Skills and Subagents native paths above require explicit opt-in for each switch through "Also install skills and subagents into the project (git-excluded)" or `update-agent <id> --provider <type> --project-resources`. Without it, their original bytes remain in managed knowledge; knowledge access is not native execution. Opt-in adds anchored paths relative to the repository top to the repository-local exclude file on the provider host, not `.gitignore`, and does not untrack files already in Git. The journal records the exclude edit so rollback removes only its entries and retains later user entries; changed ownership or markers require inspection. Non-Git projects report `resource-git-exclude-unavailable`.

### Managed knowledge launch access (2026-10-17)

`TranslationTransactionHost.knowledgeRoot` comes from `translationKnowledgeRoot()`: local agents use `<app.getPath('userData')>/provider-knowledge`, while SSH agents use `<remote HOME>/.maestro/provider-knowledge`. Local shared launches use `resolveUserDataDir()` from the host process, or the explicit `translationKnowledgeRoot` input for library hosts. SSH bindings additionally require `MAESTRO_TRANSLATION_KNOWLEDGE_REMOTE` to match the saved SSH config fingerprint and remote home; local launches reject that binding. The SSH launch wrapper verifies the current remote home and symlink boundaries, reads the index through the native port, and delivers it through the existing stdin prompt transport on each continuation. The desktop stamps `MAESTRO_USER_DATA` at startup; the isolated acceptance driver pins it inside checkout scratch. The session's `MAESTRO_TRANSLATION_KNOWLEDGE` value cannot select the trusted root. Bindings accept only a 64-hex agent hash and UUID immediately below that root, refusing redirected directories or index symlinks. Journals retain the old in-repo directory unchanged for recovery/rollback only; those paths are rejected for new bindings, and rollback still checks legacy paths against the project root.

Claude launches reuse `buildAdditionalDirArgs()` and the provider definition to grant the operation directory with `--add-dir`, and keep `--settings` with `autoMemoryDirectory` pointing to its `memory` subdirectory. Installed Claude Code `2.1.302 --help` confirms that `--add-dir` grants tool access. Regression tests verify those exact arguments and the embedded index on resume.

Codex needs no extra writable-directory grant to read managed memory. Maestro's default launch bypasses the sandbox; its read-only mode uses the provider's read-only policy. The [App Server read-access contract](https://learn.chatgpt.com/docs/app-server#sandbox-read-access-readonlyaccess) defaults read-only and workspace-write policies to full read access, with explicit restricted-root policies available separately. On macOS, installed Codex `0.163.0` ran `codex sandbox -P ':read-only' -C <scratch-project> /bin/cat <scratch-data>/provider-knowledge/<agent-hash>/<operation-id>/memory/MEMORY.md` with an isolated scratch `CODEX_HOME`: exit 0, exact synthetic body returned from outside the working directory. No model turn or real provider-home write was used. Custom policies that deny this path remain restrictions; this change does not override them. This is file-access evidence, not native recall or round-trip certification.
