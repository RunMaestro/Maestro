# Kanban Board

A live Kanban board plugin for Maestro: every open AI tab is a card, cards drag between columns, a switcher moves between one project's board and a Global board of every project, and clicking a card opens a detail pane with a description, a comment thread, a recent-History excerpt, and a message box that sends straight into that card's tab.

This document covers the trust and access path: what has to be true before `agents.dispatch` (and `transcripts.read`) will actually work at runtime, and exactly what the board shows you when any piece of that is missing. Nothing here changes behavior; it is the map of gates that already exist in the host (`src/shared/plugins/publisher-keys.ts`, `src/main/plugins/plugin-signature.ts`, `src/main/plugins/bundled-plugins.ts`, `src/main/plugins/plugin-host-handlers.ts`).

## Why this plugin needs `granted-sessions`, not an ordinary allow list

Messaging an agent (`agents:dispatch`) and reading its History (`transcripts:read`) are both declared in `plugin.json` with `"scope": "granted-sessions"` rather than an ordinary member list. That scope starts with **zero** sessions covered, no matter what the user consents to at install time - it only ever covers a session the host itself adds, one at a time, for one of two reasons:

- **the board created it** (this plugin never calls `sessions.create`, so in practice this case does not happen for Kanban Board), or
- **the user approved it**, through a one-time, host-drawn confirmation this plugin cannot see, skin, or auto-answer.

Declaring `granted-sessions` also means this plugin can never simultaneously hold `net:fetch`, `net:connect`, or `process:spawn` (`src/shared/plugins/capability-policy.ts` treats transcript reads and network egress as mutually exclusive for an untrusted plugin). `plugin.json` has none of those three capabilities, so that trade costs this plugin nothing: a board that only reads local YAML files and talks to agents the user approved has no legitimate reason to reach the network anyway.

## Everything that has to be true

For a `send-message` (→ `agents.dispatch`) or a History read (`transcripts.read`) to actually reach an agent at runtime, every one of these has to hold, in this order:

1. **The plugin is enabled.** A disabled plugin's sandboxed code never runs at all (`plugin-manager.ts`), so none of the gates below even get a chance to deny anything - there is no card, no board, nothing. This is a user toggle in Settings, not something the plugin requests.
2. **The plugin is signed with a key that verifies against the baked publisher anchor, OR the user has separately trusted it.** `verifyPluginSignature()` (`src/main/plugins/plugin-signature.ts`) hashes every file in the plugin directory, confirms that set matches `signature.json` exactly (no added, removed, or altered file), verifies the ed25519 signature over that file set, and only then checks the signer's public key against `resolveTrustedKeys()` (`src/shared/plugins/publisher-keys.ts`): the one baked-in Maestro publisher key plus whatever keys the user has added. A plugin that is unsigned, tampered, or signed by an unrecognized key is `unsigned` / `invalid` / `untrusted` respectively, and `assertTrustedActVerb()` in `plugin-host-handlers.ts` refuses every high-power act verb (`agents.dispatch` included) for anything short of `trusted`. `bundled-plugins.ts` applies the identical check before it will even seed a copy of this plugin into the user's plugins directory in the first place - an unsigned or wrongly-signed copy of this example is never auto-installed.
3. **The capability is granted.** `transcripts:read` and `agents:dispatch` each have to be consented to (the install/update prompt the user already sees for every capability), and the broker (`assertBrokerAllowed`) has to resolve the `granted-sessions` scope keyword as applying to this call before anything else runs.
4. **Unattended consent was given, separately from the capability grant.** `agents.dispatch` is "never user-present" by the host's own description: on top of the capability grant, `dispatchUnattendedAllowed(pluginId, agentId)` has to return true, or the dispatch is refused outright. This is a distinct toggle from "granted the capability" - approving the capability does not imply approving unattended sends.
5. **The target session was created by this plugin, or approved by the user.** Even with every gate above satisfied, `agents.dispatch` additionally requires `isSessionGranted(pluginId, agentId)` to be true for that exact session id (never an agent name - renaming an agent can't retarget a grant). This board creates no sessions, so in practice every grant here came from the user clicking **Allow Access** on a card's detail pane, which calls `maestro.sessions.requestAccess(sessionId)` and shows Maestro's own one-time confirmation naming the plugin, the agent, and its project. Declining leaves the session out of the grant set; it is not re-asked until the plugin restarts.
6. **The message passes the risk ceiling and the rate cap.** `assertLowOrMediumRisk()` refuses a prompt the host's own risk classifier flags as high-risk, and `ActionGuard` caps how many `agents:dispatch` calls this plugin can make per sliding window and how many can be in flight at once - a compromised-but-permitted plugin still cannot fire dispatches in a storm.

`transcripts:read` follows the same signature/capability path (steps 1-3) and the same per-session grant (step 5), but has no unattended-consent or risk-ceiling step of its own - reading History is not sending a prompt.

## What the board does when any of it is not true

- **Steps 1-2 (disabled, unsigned, tampered, or untrusted):** invisible to this README's audience, because the plugin's own code never runs, or every act verb it tries fails before the board can even draw a card. There is nothing for the board to show; Maestro's Plugins settings surface the signature/trust state directly.
- **Step 3 (capability not granted) and step 4 (no unattended consent):** the board was never able to dispatch to _any_ session in the first place, so every card renders with a "Not connected" marker and the detail pane's access gate (see below) is permanently the only thing shown in place of the History excerpt and composer - Allow Access itself will keep failing with the host's own text until these are fixed in Settings, which is outside this plugin's reach to grant.
- **Step 5 (session not created by, or approved for, this plugin):** this is the ordinary, expected state for a card the user has not yet said yes to. The card carries a small "Not connected" marker. Opening its detail pane replaces the History excerpt and the message composer with one line explaining that Kanban Board needs your OK before it can message this agent or read its History, plus an **Allow Access** button. Clicking Allow Access, or simply typing a message and hitting Send on an ungranted card, calls `maestro.sessions.requestAccess(sessionId)`; the user sees Maestro's own confirmation, never a plugin-drawn one. Approved: the pane switches to the normal excerpt and composer, and the message that was waiting gets sent automatically. Declined: the message stays right where it was typed, marked "access not granted," with a Retry action that asks again.
- **A grant revoked after the fact** (the user removes it from the allow-list editor in Settings, mid-session): the very next dispatch or History read for that session is denied with the exact same "is not granted to this plugin" message the initial-request path uses. The board recognizes that specific denial (`isGrantDenial()` in `main.js`), drops the session back out of its own in-memory granted set, clears any cached History for it, and the card returns to the ungranted state above - the same marker, the same gate, the same Allow Access button - rather than showing a generic error.
- **Step 6, the message risk ceiling:** the Send button's attempt fails and the composer shows the host's own refusal text verbatim (never a plugin-invented paraphrase), with a Retry action. Nothing is sent.
- **Step 6, the rate cap:** an in-flight or too-frequent dispatch is refused with the host's `rate limit: ...` / `concurrency limit: ...` text, shown the same way - verbatim, with Retry. The composer additionally rate-limits itself client-side to one in-flight send per card and one in-flight `requestAccess` per session, so a double Enter or a double click on Allow Access cannot itself trigger either host-side cap.

In every denial case above, the text shown on the card is the host's own error message, read out of the rejected call rather than guessed or generalized by this plugin - so what you see names exactly what is missing, and nothing here invents a friendlier-sounding but less accurate reason.

## What this plugin does not, and cannot, do

- It cannot sign itself as trusted, add itself to the publisher anchor, or override the enabled/signature/capability gates above - those are entirely host-owned, and nothing in `main.js` or `panel.html` has a code path that touches them.
- It cannot skip the one-time `sessions.requestAccess` confirmation, draw its own version of it, or pre-answer it - the dialog is drawn by the main process, parented to the main window, and defaults to Don't Allow.
- It cannot dispatch to, or read History from, any session by name - only by the exact session id the host granted, so renaming an agent never silently retargets an existing grant to a different one.
